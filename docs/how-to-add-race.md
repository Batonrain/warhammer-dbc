# Как добавить расу

Инструкция переписана по следам переезда рас из `module/constants/races.mjs`
в предметы библиотеки [packs-src/races](../packs-src/races) (план,
[этап 7](architecture-plan.md)). Расу заводит ГМ мышкой в Foundry — точно так
же, как Архетип или Родной мир, — программировать почти никогда не нужно.
Код нужен только тогда, когда правило нельзя выразить эффектом Черты; этот
случай — отдельный раздел ближе к концу файла, он не изменился с прошлой
версии инструкции.

Замысел переезда с разбором решений — отдельный документ:
[docs/superpowers/specs/2026-08-15-race-items-design.md](superpowers/specs/2026-08-15-race-items-design.md).
Читается вместе со [справочником формата](rules-format.md) — там точные
значения полей машинных правил из последнего раздела.

## Шаг 1. Завести предмет расы

В компендиуме «Расы» создать предмет типа **Раса** (для субрасы — типа
**Субраса**, см. шаг 4), положить в папку своей группы. Проще всего прямо в
Foundry: открыть компендиум, создать предмет, перетащить в нужную папку. Можно
и текстом — новый файл в `packs-src/races/<Группа>/`, тогда собрать пак
командой из шага 5.

## Шаг 2. Заполнить характеристики и тексты

Поля листа расы ([race.hbs](../templates/item/parts/race.hbs)):

| Поле | Что писать |
| --- | --- |
| Ключ | латиницей в нижнем регистре: `astartes`, `azuriane`. Зеркалится в `system.race` актора, участвует в CSS-теме (`wh-race-*`), в предикате `race` машинных правил и в требовании `reqRace`. После того как раса появилась у живых персонажей, ключ не меняют — как имя поля в базе |
| Группа | одна из четырёх меток книги: `Люди`, `Отродия`, `Аэльдари`, `Другие Ксеносы`. У группы «Аэльдари» есть второй смысл: расы этой группы считаются аэльдари везде, где раньше стояла константа `AELDARI_RACES` |
| Стартовые характеристики | не бонусы, а **значения**: применение расы кладёт их в пустые поля характеристик персонажа и не трогает уже заполненные |
| Бонусные броски | число для Мастера создания |
| Навыки / Снаряжение / Таланты | текстовые пакеты книги как есть — их разбирает Мастер создания при выдаче |
| Геносемя | галочка: раса получает органы Геносемени Астартес |
| Размер, Очки распределения, Сдвиг, Бросок Судьбы, Примечание к навыкам, Адаптации | книжная справка. Система по этим полям ничего не считает — это только текст для игрока, показанный на листе расы |
| Описание | попадает в слот расы на листе персонажа |
| Книга | как у остальных записей библиотеки |

Поле «Прошлое» (`pastRaces` — список рас, из которых можно прийти в Иннари или
Арлекина) на листе предмета не отрисовано: заполнить его можно только правкой
JSON в `packs-src/races/`, не мышкой. Нужно оно только двум записям — Иннари и
Арлекину, — остальным расам это поле не понадобится.

## Шаг 3. Добавить расовые Черты ссылками

Черты расы в схеме не хранятся: описывать их дважды означало бы держать два
источника правды об одном и том же. Вместо этого — вкладка **МЕХАНИКА (при
получении предмета)** на листе расы, тот же Конструктор, что у Родных миров и
Архетипов.

1. Открыть вкладку МЕХАНИКА, добавить группу («И» выдаёт всё сразу, «ИЛИ» при
   получении расы предлагает игроку выбрать одну запись).
2. В группе добавить запись вида «Черта».
3. Перетащить Черту из компендиума «Черты» прямо в поле записи — вкладка сама
   подсказывает: «Черту/Талант — перетащите из компендиума или с листа актора
   прямо в поле записи». Запись запоминает `sourceUuid` Черты, поэтому правка
   самой Черты (переименование, правка текста) не требует трогать расу —
   привязка держится за идентификатор, а не за имя.
4. Если у Черты есть рейтинг (X) — «Сверхъест. Ловкость (X)», «Размер (X)» —
   вписать нужное число в поле «Рейтинг» записи. Конструктор пересчитывает
   эффект Черты пропорционально рейтингу шаблона при выдаче
   (`rescaleTraitByRating` в [mechanics.mjs](../module/apps/mechanics.mjs)),
   поэтому Рейтинг 4 у «Сверхъест. Ловкость (X)» действительно даёт +4, а не
   число из шаблона.

Пример — Азуриане несут десять Черт одной «И»-группой, среди них с рейтингом:
`Unnatural Agility (X)` и `Unnatural Perception (X)`, у обеих в записи стоит
Рейтинг 4, обе дают +4 к своей характеристике.

## Шаг 4. При необходимости завести субрасу

Субраса — отдельный предмет типа **Субраса**
([subrace.hbs](../templates/item/parts/subrace.hbs)), а не поле расы: у неё
своя цена в опыте, свой бог и список Черт, которые она отменяет.

| Поле | Что писать |
| --- | --- |
| Ключ | как у расы — латиницей, зеркалится в `system.subrace` |
| Раса-родитель | ключ расы из шага 2. Субраса принимается персонажу, только если этот ключ совпадает с текущей расой — иначе лист откажет с пояснением («… — субраса …, а у персонажа …») |
| Стоимость | цена в опыте |
| Бог | если применимо (субрасы Хаоса) |
| Изменения характеристик | сдвиги поверх расовых, не значения |
| Действие / Таланты / Снимает Черты / Описание / Книга | как в тексте книги |

«Снимает Черты» — имена Черт, выданных расой, которые субраса отменяет при
применении. Писать можно одной половиной названия, как в тексте книги:
сверка (`itemHasName` из [predicates.mjs](../module/rules/predicates.mjs), тот
же помощник, что у предиката `hasTrait`) сравнивает каждую половину
двуязычного имени Черты на точное равенство — «Natural Weapons» найдёт
«Natural Weapons / Естественное Оружие», но не «Deadly Natural Weapons»: это
другая Черта, и сравнение по вхождению подстроки задело бы её тоже. Пример —
Тзаангор снимает у Зверолюда `Natural Weapons`, `Aversion to Order` и
`Stepchildren of the Gods`, а свою Черту `Tzaangor Enlightened` добавляет так
же вкладкой МЕХАНИКА, как в шаге 3.

Если книжных данных для субрасы пока нет — она существует в книге только
названием, — всё равно завести запись: ключ, имя, родитель, остальные поля
пустыми, вкладка МЕХАНИКА без записей. Пустая запись честнее пропажи: она
видна в списке субрас на листе персонажа и её можно дополнить позже, а не
заведённая запись молча исчезла бы из выбора. Так в библиотеке уже лежат
Эльданар и Серый Человек — субрасы Азуриан и Полуэльдара без своих данных.

## Шаг 5. Собрать и проверить

Если раса заводилась не в Foundry, а прямо JSON-файлом:

```bash
npm run packs:build
npm test
```

`npm test` гоняет сверку схемы `race`/`subrace` со всеми документами пака —
опечатка в поле или неполный JSON провалит тест раньше, чем расу увидит игрок.

## Если нужной Черты ещё нет в библиотеке

Завести новую Черту — предмет типа **Черта** в компендиуме «Черты» (по
традиции — в папке «Трейты_рас», но ссылка по UUID работает из любой папки):
`benefit` — текст для игрока; `hasRating`/`rating` — если Черта
параметрическая; `effects` — то, что считает система (`charBonusStat` /
`charBonusValue`, `sizeMod`, `fearRating`, `armourAll`, `initMod`, `speedMod`
и так далее — те же поля, что у остальных Черт бестиария). После этого она
подключается к расе как в шаге 3, перетаскиванием.

Шероховатость библиотеки, о которой стоит знать при вычитке: у сгенерированных
параметрических шаблонов вида «Сверхъест. Сила (X)» текст `benefit` несёт
конкретное число — то, что было у расы, которая шла первой по алфавиту среди
рас с этой Чертой. На расчёт это не влияет: рейтинг и эффект берёт сама запись
на расе (шаг 3, поле «Рейтинг»), а не текст шаблона, — но при чтении Черты
прямо в библиотеке цифра в тексте может не совпасть с тем, что реально
получит раса. Если это мешает — поправьте `benefit` шаблона на общую
формулировку («+X к Бонусу…») или заведите отдельную Черту под конкретное
число.

## Когда расе нужно машинное правило

Иногда действие Черты не сводится к плюсу в эффектах Конструктора: оно
зависит от обстоятельств броска («теряется при Размере 2+»), даёт не число, а
возможность («лечится как космодесантник»), или отменяет чужое правило по
`id`. Это по-прежнему код в [module/rules/library/](../module/rules/library/)
— переезд рас в предметы этого не коснулся, шаги ниже не изменились с прошлой
версии инструкции.

### Шаг 1. Разобрать Черту на две части

Разделение проще всего проверить вопросом: «какое число или разрешение
меняется на листе, и можно ли это выразить одним из видов эффекта, которые
уже умеет Конструктор ([таблица](rules-format.md#эффекты))?» Если ответ
да — Черта идёт в шаг 3 основной инструкции, ссылкой. Если ответ зависит от
обстоятельств броска («работает, только пока Размер не больше 3») — нужно
машинное правило, оно ниже.

Бывает и третий случай, честно неприятный: у «Amphibious / Амфибия» Астартес
`benefit` в библиотеке Черт — переброс провальных тестов Атлетики (Плавание),
и для него **не хватает вида эффекта вовсе**: реестр `EFFECT_KINDS`
([effects.mjs](../module/rules/effects.mjs)) не знает переброса, а область
эффекта в конвейере теста различает навык целиком (`skill:athletics`), не
специализацию, — так что даже появись вид эффекта, широкий переброс всей
Атлетики был бы уже другим правилом. Такая Черта остаётся текстом `benefit`
без записи в МЕХАНИКЕ расы, и это не то, что чинится по этой инструкции: новый
вид эффекта — правка `module/rules/effects.mjs` и конвейера теста, программная
задача, а не заполнение данных.

### Шаг 2. Записать правило

Файл книги в [module/rules/library/](../module/rules/library/), по образцу
[astartes.mjs](../module/rules/library/astartes.mjs). Пример — вымышленная
Черта новой расы «Хищный Нюх», текст которой «+10 к тестам Бдительности, пока
Размер персонажа не больше 3»:

```js
export const AZURIANE_RULES = [
  {
    id: "azuriane.predator.scent",
    label: "Predator's Scent / Хищный Нюх",
    when: { sizeMax: 3 },
    effects: [{ kind: "rollBonus", target: "skill:awareness", value: 10 }]
  }
];
```

Три поля обязательны.

**`id`** — имя правила в системе. Пишется латиницей в нижнем регистре, точка
разделяет уровни. По этому имени одно правило вытесняет другое, поэтому после
выхода релиза `id` не меняют, как не меняют имя поля в базе.

**`label`** — двуязычное название, как в книге. Его видит игрок в диалоге
броска и в карточке в чате.

**`effects`** — список эффектов. Вид эффекта (`kind`) берётся из
[таблицы справочника](rules-format.md#эффекты), придумывать свой нельзя:
неизвестный вид не сработает и пожалуется в консоль.

Поле `when` нужно, только когда правило зависит от обстоятельств: «теряется
при Размере 2+» становится `sizeMax: 1`. Проверку самой расы писать не
надо — её уже делает источник правил из шага 3.

### Шаг 3. Привязать правило к расе

Поле `rules` у предмета расы больше не существует — `RaceData` его не несёт,
и добавлять его в схему не нужно. Вместо этого правила расы держит карта в
[rules/sources.mjs](../module/rules/sources.mjs):

```js
import { AZURIANE_RULES } from "../rules/library/aeldari.mjs";

const RACE_RULES = { astartes: ASTARTES_RULES, azuriane: AZURIANE_RULES };
```

Добавить импорт наверху файла и одну запись в `RACE_RULES` — с ключом расы из
шага 2 основной инструкции. Больше нигде ничего не меняется: источник `race`
уже сам читает `system.race` актора.

### Шаг 4. Проверить

Тест на правило пишется рядом с правилом, в
[test/rules/library/](../test/rules/library/), по образцу
[astartes.test.mjs](../test/rules/library/astartes.test.mjs). Трёх проверок
достаточно:

```js
it("собирается у азуриан", () => {
  expect(collectRules(actor({ race: "azuriane" })).map(r => r.id))
    .toContain("azuriane.predator.scent");
});

it("не собирается у людей", () => {
  expect(collectRules(actor({ race: "human" }))).toEqual([]);
});

it("даёт +10 к Бдительности только при Размере ≤3", () => {
  expect(collectRules(actor({ race: "azuriane", size: 3 })).flatMap(r => r.effects))
    .toContainEqual({ kind: "rollBonus", target: "skill:awareness", value: 10 });
  expect(collectRules(actor({ race: "azuriane", size: 4 }))).toEqual([]);
});
```

Подставной актор — обычный объект `{ system: { race: "azuriane", size: 3 },
items: [] }`, без Foundry. Запускать саму игру не требуется:

```text
npm test
```

Зелёный прогон означает, что правило собирается там, где должно, и не
собирается там, где не должно.

### Когда у расы своя версия общего правила

Правило может отменить другое по его `id`:

```js
{
  id: "smite.astartes",
  overrides: ["smite.baseline"],
  when: { race: ["astartes"] },
  effects: [{ kind: "damageDice", target: "power:smite", value: "1d10+PR" }]
}
```

Обе версии лежат рядом и обе читаемы. У Астартес действует вторая, у
остальных первая. Копировать код не нужно
([пример с проверкой](../test/rules/psychic-overrides.test.mjs)).

### Когда правило не про число, а про возможность

«Лечится как космодесантник», «доступна папка талантов Геносемени» — это не
модификатор, а разрешение. Такие правила выдают возможность по имени:

```js
{ id: "astartes.physiology",
  label: "Физиология Астартес",
  effects: [{ kind: "grantFlag", target: "healing.astartes" }] }
```

Код спрашивает возможность, а не расу:
`hasRuleFlag(actor, "healing.astartes")`. Поэтому Черта Арлекина «лечится как
космодесантник» получит ту же строку из своих данных, и в коде листа править
ничего не придётся.

Имена возможностей перечислены в [справочнике](rules-format.md#возможности).
Новое имя придумывается только вместе с местом, которое его спрашивает: флаг,
которого никто не читает, не работает и об этом не сообщает.

## Чего делать не стоит

**Не придумывать числа.** В машинную часть попадает то, что написано в книге.
Если в книге числа нет, правила нет.

**Не удалять текст `benefit`.** Машинная часть Черты и машинное правило
добавляются рядом с ним, а не вместо.

**Не писать `kind: "script"`.** Свободный код в правиле возвращает нас туда,
откуда мы уходили. Это аварийный выход, и к нему пишут объяснение, почему
иначе не вышло.

**Не заводить условие там, где хватает значения.** Если у расы просто другое
число Черты — это поле «Рейтинг» записи МЕХАНИКА (шаг 3 основной инструкции),
а не новый предикат в машинном правиле.
