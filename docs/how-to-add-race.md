# Как добавить расу

Инструкция написана по следам этапа 3 [плана](architecture-plan.md): так расовые
Черты Астартес переехали из кода в данные. Программировать не нужно, нужно
аккуратно переписать текст книги в таблицу.

Читается вместе со [справочником формата](rules-format.md): здесь порядок
действий, там точные значения полей.

## Что где лежит

| Файл | Что в нём |
| --- | --- |
| [module/constants/races.mjs](../module/constants/races.mjs) | описание расы для игрока: характеристики, Черты, снаряжение |
| [module/rules/library/](../module/rules/library/) | машинная часть Черт, по файлу на книгу |
| [test/rules/library/](../test/rules/library/) | проверки: правило собирается у нужной расы и не собирается у чужой |

Текст Черты остаётся в `races.mjs` и не удаляется никогда. Игрок читает
описание, система применяет правило, а тест ловит расхождение между ними.

## Шаг 1. Разобрать Черту на две части

Возьмём Черту Азуриан из `races.mjs`:

```js
{ name: "Unnatural Agility (4) / Сверхъест. Ловкость (4)",
  benefit: "+4 к Бонусу Ловкости.", rating: 4, hasRating: true, effects: {} }
```

В машинную часть идёт то, что считает система: «+4 к Бонусу Ловкости». Всё
остальное — работа мастера, и она остаётся текстом.

Разделение проще всего проверить вопросом: «какое число изменится на листе?».
Если ответа нет, правило не пишется. У Астартес так остались две Черты из шести:

- «Амфибия» перебрасывает Плавание, а область эффекта различает только навык
  целиком, не специализацию;
- «Проворный» даёт штраф тому, кто атакует, а атаки перейдут на общий конвейер
  только на шаге 5.2 плана.

Обе ждут подходящей области эффекта и живут в тексте. Это нормальное состояние,
а не недоделка: правило без механики хуже отсутствия правила.

## Шаг 2. Записать правило

Файл книги в [module/rules/library/](../module/rules/library/), по образцу
[astartes.mjs](../module/rules/library/astartes.mjs):

```js
export const AZURIANE_RULES = [
  {
    id: "azuriane.unnatural.agility",
    label: "Unnatural Agility (4) / Сверхъест. Ловкость (4)",
    effects: [{ kind: "charBonus", target: "ag", value: 4 }]
  }
];
```

Три поля обязательны.

**`id`** — имя правила в системе. Пишется латиницей в нижнем регистре, точка
разделяет уровни. По этому имени одно правило вытесняет другое, поэтому после
выхода релиза `id` не меняют, как не меняют имя поля в базе.

**`label`** — двуязычное название, как в книге. Его видит игрок в диалоге броска
и в карточке в чате.

**`effects`** — список эффектов. Вид эффекта (`kind`) берётся из
[таблицы справочника](rules-format.md#эффекты), придумывать свой нельзя:
неизвестный вид не сработает и пожалуется в консоль.

Поле `when` нужно, только когда правило зависит от обстоятельств: «теряется при
Размере 2+» становится `sizeMax: 1`. Проверку самой расы писать не надо — её уже
сделал источник правил из шага 3.

## Шаг 3. Привязать правила к расе

В `races.mjs` рядом с `traits` добавляется поле `rules`, а наверху файла — импорт:

```js
import { AZURIANE_RULES } from "../rules/library/aeldari.mjs";

  azuriane: {
    traits: [ /* текст как был */ ],
    rules: AZURIANE_RULES,
  }
```

Больше нигде ничего не меняется: источник `race`
([sources.mjs](../module/rules/sources.mjs)) сам находит это поле у расы актора.

## Шаг 4. Проверить

Тест на правило пишется рядом с правилом, в
[test/rules/library/](../test/rules/library/), по образцу
[astartes.test.mjs](../test/rules/library/astartes.test.mjs). Трёх проверок
достаточно:

```js
it("собирается у азуриан", () => {
  expect(collectRules(actor({ race: "azuriane" })).map(r => r.id))
    .toContain("azuriane.unnatural.agility");
});

it("не собирается у людей", () => {
  expect(collectRules(actor({ race: "human" }))).toEqual([]);
});

it("даёт +4 к бонусу Ловкости", () => {
  expect(collectRules(actor({ race: "azuriane" })).flatMap(r => r.effects))
    .toContainEqual({ kind: "charBonus", target: "ag", value: 4 });
});
```

Подставной актор — обычный объект `{ system: { race: "azuriane" }, items: [] }`.
Запускать Foundry не требуется:

```text
npm test
```

Зелёный прогон означает, что правило собирается там, где должно, и не собирается
там, где не должно.

## Когда у расы своя версия общего правила

Это тот случай, ради которого затевалась вся переделка. Правило может отменить
другое по его `id`:

```js
{
  id: "smite.astartes",
  overrides: ["smite.baseline"],
  when: { race: ["astartes"] },
  effects: [{ kind: "damageDice", target: "power:smite", value: "1d10+PR" }]
}
```

Обе версии лежат рядом и обе читаемы. У Астартес действует вторая, у остальных
первая. Копировать код не нужно
([пример с проверкой](../test/rules/psychic-overrides.test.mjs)).

## Когда правило не про число, а про возможность

«Лечится как космодесантник», «доступна папка талантов Геносемени» — это не
модификатор, а разрешение. Такие правила выдают возможность по имени:

```js
{ id: "astartes.physiology",
  label: "Физиология Астартес",
  effects: [{ kind: "grantFlag", target: "healing.astartes" }] }
```

Код спрашивает возможность, а не расу:
`hasRuleFlag(actor, "healing.astartes")`. Поэтому Черта Арлекина «лечится как
космодесантник» получит ту же строку из своих данных, и в коде листа править
ничего не придётся.

Имена возможностей перечислены в [справочнике](rules-format.md#возможности).
Новое имя придумывается только вместе с местом, которое его спрашивает: флаг,
которого никто не читает, не работает и об этом не сообщает.

## Чего делать не стоит

**Не придумывать числа.** В машинную часть попадает то, что написано в книге. Если
в книге числа нет, правила нет.

**Не удалять текст `benefit`.** Машинная часть добавляется рядом с ним.

**Не писать `kind: "script"`.** Свободный код в правиле возвращает нас туда,
откуда мы уходили. Это аварийный выход, и к нему пишут объяснение, почему иначе
не вышло.

**Не заводить условие там, где хватает значения.** Если у расы просто другое
число, это поле в данных расы, а не новый предикат.
