# Формат правил

Справочник к этапам 1–3 [плана](architecture-plan.md). Описывает, как записать
игровое правило данными вместо кода.

## Зачем это нужно

Сейчас правило существует как русский текст:

```js
// module/constants/races.mjs
{ name: "Nimble / Проворный",
  benefit: "Атакующим по нему −A.b к попаданию.",
  effects: {} }
```

Человек прочитает, система применить не сможет. Поэтому каждое действующее правило
пишется отдельно, кодом, и расходится с текстом при первой же правке.

Формат ниже добавляет машинную часть **рядом** с текстом. Текст остаётся описанием
для игрока и не удаляется никогда.

## Форма записи

```js
{
  id:        "eldarten",              // обязателен, уникален в системе
  label:     "Eldarten / Эльдарское Тело",
  when:      { /* условия */ },       // пусто = действует всегда
  effects:   [ /* эффекты */ ],
  overrides: [ "id_другого_правила" ] // необязательно
}
```

`id` пишется в нижнем регистре, точка разделяет уровни: `smite.astartes`,
`aeldari.path.warlock`. По этому идентификатору правило вытесняется другим, поэтому
менять его после выхода релиза нельзя, как нельзя менять имя поля в базе.

## Условия (`when`)

Правило действует, когда истинны **все** условия одновременно. Пустой `when`
означает «всегда».

| Ключ | Значение | Истинно, когда | Есть |
| --- | --- | --- | --- |
| `race` | массив ключей рас | раса актора в списке | да |
| `subrace` | массив ключей субрас | субраса актора в списке | да |
| `alignment` | массив мировоззрений | мировоззрение актора в списке | нет |
| `sizeMax` | число | итоговый Размер не больше указанного | да |
| `sizeMin` | число | итоговый Размер не меньше указанного | нет |
| `charMin` | объект `{ ключ: число }` | все указанные характеристики не ниже порога | да |
| `hasTalent` | строка или массив | у актора есть талант с таким именем | да |
| `hasTrait` | строка или массив | у актора есть черта с таким именем | да |
| `psyRatingMin` | число | пси-рейтинг не ниже указанного | нет |
| `weaponClass` | массив | класс оружия в контексте броска подходит | да |
| `discipline` | массив | дисциплина психосилы в контексте подходит | нет |
| `targetHasTrait` | строка или массив | у цели есть такая черта | да |
| `hasFaction` | строка или массив | актор состоит в такой фракции или в нижестоящей | да |
| `targetHasFaction` | строка или массив | то же про цель броска | да |

Столбец «Есть» — реализовано ли условие сейчас. Восемь предикатов покрывают
существующий контент, остальные добавляются, когда под них появляются данные.
Правило с нереализованным условием не действует и жалуется в консоль, как при
опечатке: молча не сработать оно не может.

Одиночное значение везде читается как список из одного элемента: `race: "human"`
и `race: ["human"]` — одно и то же.

Подпись предиката всегда одна:

```js
// module/rules/predicates.mjs
export const PREDICATES = {
  race:    (actor, ctx, value) => list(value).includes(actor?.system?.race),
  sizeMax: (actor, ctx, value) => sizeOf(actor) <= Number(value),
  charMin: (actor, ctx, value) => Object.entries(value ?? {}).every(
             ([k, n]) => (Number(actor?.system?.characteristics?.[k]?.total) || 0) >= n),
  weaponClass: (actor, ctx, value) => list(value).includes(ctx?.weapon?.system?.weaponClass)
};
```

Про Размер: у актора их два поля. Базовый лежит в `system.size`, вклад Черт — в
`system.sizeMod`, сумму лист кладёт в `system.sizeTotal`. `sizeOf` берёт готовую
сумму, а без неё складывает сам, потому что у подставного актора в тесте
посчитанного поля нет.

Про `hasTalent` и `hasTrait`: список означает «и». Правило, которому подходит
любой из двух Талантов, пишется двумя правилами; правило, требующее оба сразу,
иначе не записать. Оба предиката ищут и среди Талантов, и среди Черт, а имя
сравнивают по любой половине двуязычного названия: `"Gene-Seed"` и
`"Геносемя"` найдут один и тот же предмет, а `"Resistance"` найдёт
`"Resistance (Cold) / Сопротивление (Холод)"`.

Про `hasFaction` и `targetHasFaction`: фракция — предмет на листе, поэтому актор
может состоять сразу в нескольких (астартес-предатель — и Хаос, и свой легион).
Отбор односторонний: условие «Хаос» подходит роте в составе его легиона, условие
«III рота» весь Хаос не покрывает. Дерево строится по ссылке `parent` у самих
Фракций и живёт в реестре ([factions.mjs](../module/rules/factions.mjs)),
который наполняет сторона Foundry при готовности мира — до этого условие просто
не срабатывает.

У `targetHasFaction` два источника, и они не пересекаются: в бою цель это
выделенный токен (`ctx.targetActor`), а в социальном тесте токена нет вовсе —
«Инквизицию» мышью не выделишь, — поэтому игрок выбирает фракцию собеседника в
диалоге, и она приезжает в `ctx.socialFaction`. Выбор в диалоге важнее токена.

Про `targetHasTrait`: актор цели лежит в `ctx.targetActor`. Имя `ctx.target` в том
же объекте занято флагом «бросок нацелен» — его читает матчер ситуативных
модификаторов ([match-context.mjs](../module/rules/match-context.mjs)), и на этапе
2 оба контекста сошлись в одном объекте. Поэтому переименован предикат, а не
данные: галочки с `when.target` лежали в Особенностях Происхождений, и
переименование в них потребовало бы миграции. (Та галочка, ради которой это
делалось, — «Паранойя Выжившего» Мира смерти — с тех пор стала возможностью
`attack.surpriseImmune`, см. «Возможности» ниже; сам флаг матчера остался.)

Три требования к предикату, и они не обсуждаются:

1. **Чистая функция.** Никаких обращений к `game`, `ui`, `canvas`, никаких бросков.
   Иначе правило не протестировать без запуска Foundry, а весь смысл был в этом.
2. **Безопасен к отсутствию данных.** У подставного актора в тесте может не быть
   половины полей. Отсюда `?.` и `?? 0` в каждом обращении.
3. **Возвращает строго `true` или `false`.** Не `undefined`, не число.

Неизвестный ключ условия даёт ошибку в консоль и `false`. Опечатка в данных не
должна проходить молча: тихо не сработавшее правило ищется днями.

## Эффекты

| `kind` | Поля | Что делает |
| --- | --- | --- |
| `charBonus` | `target`, `value` | плюс к бонусу характеристики (Unnatural) |
| `charTotal` | `target`, `value` | плюс к значению характеристики |
| `rollBonus` | `target`, `value` | модификатор к тесту |
| `rollMode` | `target`, `mode`, `rolls` | несколько бросков с выбором (`keepBest`, `keepWorst`) |
| `penaltyMul` | `target`, `factor` | множитель штрафов, `0.5` = половина |
| `apBonus` | `target`, `value` | броня по локации или `all` |
| `damageBonus` | `target`, `value` | плюс к урону |
| `damageDice` | `target`, `value` | замена формулы урона |
| `grantValue` | `target`, `value` | плюс к производному полю (реакции, скорость) |
| `grantFlag` | `target` | возможность по имени, см. «Возможности» ниже |
| `fearRating` | `value` | рейтинг страха, берётся максимум, не сумма |
| `grantItem` | `uuid`, `qty` | выдать предмет при получении источника |
| `script` | `code` | аварийный выход, см. предупреждение ниже |

`target` для бросков пишется с областью через двоеточие: `initiative`,
`skill:psyniscience`, `char:wp`, `power:smite`, `attack`, `weapon:melee`. Область
`all` или пустая означает «в любом тесте». Есть и `social` — все социальные
навыки книги разом (Обаяние, Командование, Коммерция, Обман, Дознание, Допрос,
Запугивание). Своего перечня у неё нет: признак берётся из таблицы навыков
(`apt2: "social"`), иначе два списка разошлись бы при добавлении навыка.
Проницательность помечена общей и сюда не входит — так в книге. У `grantValue` и `grantFlag` в том же
поле лежит имя: производного поля («reactions», «sizeMod») или возможности.

Области атаки, появившиеся на шаге 5.2:

| Область | Куда попадает |
| --- | --- |
| `attack` | любой удар и выстрел |
| `weapon:melee` | рукопашные, включая метательные |
| `weapon:ranged` | стрелковые |
| `weapon:<класс>` | конкретный класс: `pistol`, `basic`, `heavy`, `launcher`… |

Область сопоставляется с контекстом броска в
[resolve-test.mjs](../module/rules/resolve-test.mjs). Тест навыка и тест
характеристики различаются наличием `ctx.skill`, поэтому `char:int` действует
только на тест Интеллекта и не подхватывается броском навыка на Интеллекте: иначе
одна запись означала бы два разных правила книги. По той же причине атака
отбирается отдельной веткой и не подхватывает `char:ws`: «+10 к тестам
Оружейного Мастерства» и «+10 ко всем ударам» — два разных правила книги.
Область `power:` не совпадает ни с чем: психосилы на конвейер ещё не переведены.

### Значение, зависящее от цели

Иногда числа в данных быть не может: «Проворный» даёт атакующему минус Бонус
Ловкости **цели**, а он у каждой цели свой. Такие правила вместо `value` пишут
`valueFrom`, и значение считается на каждый бросок:

```js
effects: [{
  kind: "rollBonus",
  target: "attack",
  valueFrom: { targetCharBonus: "ag", multiplier: -1 }
}]
```

Известен один источник — `targetCharBonus` (бонус характеристики цели);
`multiplier` необязателен и по умолчанию равен 1. Неизвестный источник не
превращается молча в ноль, а жалуется в консоль, и галочка не появляется.

Цель берётся из `ctx.targetActor` — того же поля, что читает предикат
`targetHasTrait`. Если цель не выбрана, значение равно нулю, но правило с
условием по цели до этого и не доберётся: отбор его не пропустит.

До диалога броска доходят два вида эффектов: `rollBonus` даёт галочку со своим
значением, `penaltyMul` с `factor: 0.5` — галочку «ополовинить штраф». Другого
множителя диалог не умеет, и правило с ним не применяется молча, а жалуется в
консоль. Остальные виды подключаются вместе с фазами 5–6 конвейера.

Про `fearRating`: складывать нельзя. Два источника с рейтингом 2 дают 2, а не 4.
Это уже учтено в существующем коде
([effect-keys.mjs](../module/constants/effect-keys.mjs), тип `upgrade`), и новый
реестр должен вести себя так же.

Про `script`: свободный JS в правиле возвращает нас туда, откуда мы уходили.
Допустим только когда правило действительно нельзя выразить данными, и в этом
случае к нему пишется комментарий с объяснением, почему.

## Возможности

Часть правил книги не меняет числа, а разрешает: «лечится как космодесантник»,
«доступна папка талантов Геносемени». В коде такое жило проверкой расы, и вторая
раса с тем же свойством требовала правки кода. Эффект `grantFlag` выдаёт
возможность по имени, а код её спрашивает:

```js
// module/rules/flags.mjs
import { hasRuleFlag } from "../rules/flags.mjs";

if (hasRuleFlag(patient, "healing.astartes")) { /* … */ }
```

Имя возможности — название правила книги, а не расы, даже когда раса в нём
упомянута. `healing.astartes` читается как «лечится как космодесантник», и Черта
Арлекина «Искажённое Тело» с той же оговоркой получит ту же строку из своих
данных, не тронув код листа.

Возможности, которые кто-то спрашивает сейчас:

| Имя | Что открывает | Кто спрашивает |
| --- | --- | --- |
| `healing.astartes` | пассивное лечение считается Отдыхом, Отдых — Постельным режимом | `_applyHealing` |
| `unarmed.astartesProfile` | усиленный профиль безоружного удара (стр. 40) | `_showAttackDialogNoWeapon` |
| `talents.geneSeed` | папка талантов «Геносемя» в пикере | `_talentGroupLock` |
| `fate.save` | трата Очка Судьбы/Бесчестья может не состояться (1d10, при 1 возврат) | хук `updateActor`, [fate-save.mjs](../module/rules/fate-save.mjs) |
| `assist.beyondCap` | помощник встаёт сверх лимита и слот не занимает | `assistRejection` |
| `attack.surpriseImmune` | по носителю не работает «Цель Врасплох» (+30) | `showAttackDialog` |
| `fear.faithInThePast` | кнопка «Вера в прошлое» в карточке проваленного Страха | `_executeFearRoll` |

Последние четыре — Особенности Происхождений
([library/homeworlds.mjs](../module/rules/library/homeworlds.mjs)). Они
показывают, зачем возможности вообще нужны: каждая вмешивается в СВОЮ точку
системы, и ни одна не выражается ни модификатором, ни выдачей предмета. Раньше
такие Особенности жили именованными ключами со своим сканом предметов
(`kind:"specialRule"` на ветке «Конструктор-и-происхождения»); отдельный
механизм рядом с реестром правил не понадобился — хватило `grantFlag`.

Возможность, гасящая чужой модификатор, спрашивается **у цели, без контекста
броска**: контекст описывает бросок атакующего, и правило цели про чужое оружие
ничего не знает. Гашеное показываем зачёркнутым, а не убираем из списка — игрок
должен видеть, ПОЧЕМУ бонуса нет. Подпись правила-источника для таких мест даёт
`ruleFlagLabels(actor, flag)`.

Разовые возможности («один раз за столкновение») отмечаются на самом акторе:
`flags.warhammer-dbc.usageLimits.<возможность>` — предмета-носителя у правила
нет, поэтому предметная метка `usageLimit` тут не годится. Обе сбрасывает
кнопка «Новая сцена» ([game-session.mjs](../module/apps/game-session.mjs)).

Два правила про имена. Первое: новое имя заводится вместе с местом, которое его
читает, иначе флаг молча ничего не делает. Второе: возможность подчиняется отбору
как любой эффект — правило, не прошедшее `when`, её не выдаёт, иначе флаг стал бы
просто вторым названием расы.

## Вытеснение (`overrides`)

Механизм, ради которого затевался весь план. Правило может отменить другое по его
идентификатору. Это и есть ответ на «у эльдар этот талант работает иначе» и «у
Астартес своя версия психосилы».

```js
// Базовая версия
export const SMITE = {
  id: "smite.baseline",
  effects: [{ kind: "damageDice", target: "power:smite", value: "1d10" }]
};

// Версия Астартес вытесняет базовую
export const SMITE_ASTARTES = {
  id: "smite.astartes",
  overrides: ["smite.baseline"],
  when: { race: ["astartes"], hasTrait: "Gene-Seed" },
  effects: [{ kind: "damageDice", target: "power:smite", value: "1d10+PR" }]
};
```

У астартеса действует вторая, у человека первая. Форк кода не нужен, обе версии
лежат рядом и обе читаемы.

Порядок разбора в `collectRules`: сначала собрать все правила от всех источников,
потом отобрать по `when`, и **только потом** снимать вытесненные. Наоборот нельзя:
правило с невыполненным условием не должно ничего вытеснять.

Если два прошедших отбор правила вытесняют друг друга, это ошибка в данных.
Пишем в консоль и оставляем оба: молча выбирать одно из двух хуже, чем показать
двойной эффект, который сразу заметят.

## Источники правил

Правила приходят из разных мест, а собираются в один список.

```js
// module/rules/sources.mjs
registerRuleSource("race",      a => RACES[a.system.race]?.rules ?? []);
registerRuleSource("subrace",   a => SUBRACES[a.system.subrace]?.rules ?? []);
registerRuleSource("homeworld", a => HOMEWORLD_BY_KEY[hwKey(a)]?.rules ?? []);
registerRuleSource("path",      a => pathRules(a));
registerRuleSource("items",     a => a.items.flatMap(i => i.system.rules ?? []));
```

Добавить книгу означает зарегистрировать источник и положить данные. Ядро не
меняется. Реестр подсистем
[features.mjs](../module/constants/features.mjs) уже умеет включать и выключать
книги, и выключенная книга должна убирать свои правила из сборки автоматически.

## Полный пример

Черта эльдар «Eldarten» из
[races.mjs](../module/constants/races.mjs). В книге это абзац на десять строк.
Машинная часть:

```js
export const ELDARTEN = {
  id: "aeldari.eldarten",
  label: "Eldarten / Эльдарское Тело",
  when: {
    race: ["azuriane", "drukhari", "harlequin", "exodite"],
    sizeMax: 1                       // «теряется при Размере 2+»
  },
  effects: [
    { kind: "grantValue", target: "reactions",  value: 1 },
    { kind: "rollBonus",  target: "initiative", value: 4 },
    { kind: "rollMode",   target: "initiative", mode: "keepBest", rolls: 3 },
    { kind: "penaltyMul", target: "skill:psyniscience", factor: 0.5 }
  ]
};
```

Оговорка «теряется при Размере 2+» стала условием `sizeMax: 1`, а не примечанием,
которое надо помнить. Остальные пункты черты (иммунитет к людским болезням,
долгожительство, отношение слаанешитских ветвей) в машинную часть не переводятся:
их применяет мастер, и они остаются в тексте `benefit`. Переводить в данные надо
то, что система считает, а не всё подряд.

## Как проверять

Правило тестируется на литерале, без Foundry:

```js
import { describe, it, expect } from "vitest";
import { matchRule } from "../module/rules/collect.mjs";
import { ELDARTEN } from "../module/rules/library/aeldari.mjs";

const actor = (over = {}) => ({
  system: { race: "azuriane", sizeMod: 0, characteristics: {}, ...over },
  items: []
});

describe("Eldarten", () => {
  it("действует у азуриан обычного размера", () => {
    expect(matchRule(ELDARTEN, actor(), {})).toBe(true);
  });

  it("не действует при Размере 2", () => {
    expect(matchRule(ELDARTEN, actor({ sizeMod: 2 }), {})).toBe(false);
  });

  it("не действует у людей", () => {
    expect(matchRule(ELDARTEN, actor({ race: "human" }), {})).toBe(false);
  });
});
```

Три теста на правило: подходит, не подходит по основному условию, не подходит по
