# План архитектурных исправлений

Цель: сделать так, чтобы вариативные правила (раса, фракция, архетип, дисциплина)
описывались данными, а не кодом. Побочный результат: систему станет возможно
проверять автотестами и править контент без программиста.

## Как пользоваться планом

Этапы идут по порядку. Каждый следующий опирается на предыдущий, перескакивать не
стоит: этапы 4–6 без реестра правил из этапа 1 придётся делать дважды.

Внутри этапа шаги пронумерованы. У каждого есть строка **Готово, когда** —
проверяемый признак завершённости. Если признак не выполняется, шаг не закрыт,
даже когда код написан.

Отметки размера: **S** до часа, **M** до дня, **L** несколько дней, **XL** недели.

## Три правила на весь план

1. **Новое живёт рядом со старым.** Ни один этап не начинается с удаления
   работающего кода. Сначала новый механизм работает параллельно, потом старый
   снимается по частям.
2. **Ветка на этап, не на весь план.** Ветвление длиной в месяц не сольётся:
   [actor-sheet.mjs](../module/sheets/actor-sheet.mjs) правят все.
3. **Каждый шаг проверяем.** Пока правила зашиты в интерфейс, проверка ручная:
   открыть лист, бросить кубик, сравнить число. Начиная с этапа 1 появляются тесты,
   и ручную проверку заменяет `npm test`.

## Этап 1. Реестр правил

**Зачем:** появляется единственное место, где живут условия и эффекты. Существующий
код не меняется, только получает новую опору.

**Размер:** L. **Риск:** нет, старые пути исполнения не затрагиваются.

Формат записи правила описан отдельно: [rules-format.md](rules-format.md). Этот
документ читается до начала шага 1.2.

### 1.1. Завести папку `module/rules/` ✅

Файлы-заготовки, пока пустые:

```text
module/rules/
  predicates.mjs      // реестр условий
  effects.mjs         // реестр видов эффектов
  sources.mjs         // реестр источников правил
  collect.mjs         // matchRule + collectRules(actor, ctx)
  match-context.mjs   // матчер контекста броска, приехал на шаге 1.4
  library/            // сами правила по книгам
    core.mjs
    astartes.mjs
    aeldari.mjs
```

`effects.mjs` и три файла библиотеки остаются заготовками: применение эффектов —
этап 2, наполнение библиотеки — этап 3. `effects.mjs` уже держит перечень
известных `kind` и обязательных полей, чтобы таблица из
[rules-format.md](rules-format.md) жила в одном месте с кодом.

**Готово, когда:** папка создана, файлы импортируются друг из друга без ошибок,
`npm run lint` чистый. Проверяется тестом `test/rules/scaffold.test.mjs`.

### 1.2. Реестр предикатов ✅

`module/rules/predicates.mjs`. Каждый предикат — чистая функция
`(actor, ctx, value) => boolean`. Ни обращений к `game`, ни к интерфейсу: это
условие для теста в первую очередь.

Начать с восьми, которых хватает на существующий контент:
`race`, `subrace`, `sizeMax`, `hasTalent`, `hasTrait`, `charMin`, `weaponClass`,
`targetHasTrait`. Точные подписи в [rules-format.md](rules-format.md).

Три места, где реализация уточнила справочник (там он уже поправлен):

- `sizeMax` смотрит на итоговый Размер, а не на одно поле. У актора базовый
  Размер лежит в `system.size`, вклад Черт — в `system.sizeMod`, сумма — в
  `system.sizeTotal` ([actor.mjs:1162](../module/documents/actor.mjs)). Предикат
  берёт `sizeTotal`, а при его отсутствии складывает сам: у подставного актора в
  тесте посчитанного поля нет.
- Список в `hasTalent` и `hasTrait` означает «и», а не «или». Правило с
  альтернативами записывается двумя правилами, а требование двух Талантов сразу
  иначе не выразить.
- Оба предиката ищут и по Талантам, и по Чертам, и сравнивают имя по любой
  половине двуязычного названия. Так же ведёт себя разборщик требований талантов
  ([talent-requirements.mjs:199](../module/constants/talent-requirements.mjs)).

**Готово, когда:** `test/rules/predicates.test.mjs` проверяет каждый предикат на
подставном объекте актора (обычный литерал `{ system: { race: "astartes" } }`,
никакого Foundry), все тесты зелёные. Сейчас: 26 тестов.

### 1.3. Функция отбора `matchRule` ✅

Одна функция: правило подходит контексту, если **все** его условия истинны.
Неизвестный ключ условия — ошибка в консоль и `false`, чтобы опечатка в данных не
проходила молча. Живёт в `collect.mjs`: оттуда её импортирует пример проверки
правила в [rules-format.md](rules-format.md).

Под это же правило попадают условия, описанные в справочнике, но ещё не
реализованные (`alignment`, `sizeMin`, `psyRatingMin`, `discipline`): пока
предиката нет, правило с таким условием не действует и жалуется в консоль.

**Готово, когда:** тест проверяет три случая: все условия истинны, одно ложно,
ключ условия неизвестен.

### 1.4. Переселить `matchesContext` из контентного файла ✅

Сейчас общий матчер лежит в
[homeworlds.mjs:424](../module/constants/homeworlds.mjs) и импортируется листом
персонажа: контентный файл раздаёт механизм, это перевёрнутая зависимость.

1. Перенести тело `matchesContext` в `module/rules/match-context.mjs`.
2. В `homeworlds.mjs` оставить реэкспорт. Функция там ещё и вызывается
   (`homeworldRollMods`), поэтому не `export … from`, а импорт и реэкспорт:

   ```js
   import { matchesContext } from "../rules/match-context.mjs";
   export { matchesContext };
   ```

   Так [actor-sheet.mjs:64](../module/sheets/actor-sheet.mjs) продолжает работать
   без правок.
3. Накрыть перенесённую функцию тестами: контексты навыка, характеристики,
   специализации и флаговые (`suppression`, `single`, `target`).

**Готово, когда:** тесты зелёные, лист персонажа открывается, галочки Особенности
Происхождения появляются в диалоге броска навыка как раньше. Тестами закрыто
и то, что реэкспорт указывает на ту же функцию, и отбор Особенностей через
`homeworldRollMods`; открытие листа проверяется руками в Foundry.

Подсистема называется «Происхождения»
([features.mjs](../module/constants/features.mjs), ключ `homeworlds`), и так же
она подписана в шапке листа. «Родной мир» — название книги-источника, в
интерфейс оно не выходит. В новых файлах пишем «Происхождение»; технические
имена (`homeworld` как тип предмета, `homeworlds` как ключ настройки) остаются
прежними, их переименование — отдельная задача с миграцией данных.

При проверке этого пути нашлась течь выключателя. `homeworlds` выключен, а
галочки Особенности в диалоге броска остаются: выбор из шапки листа пропадает
(`homeworldSheetContext` начинается с `isFeatureEnabled`), а
[`_homeworldModsHtml`](../module/sheets/actor-sheet.mjs) такой проверки не имел.
Добавлена — по образцу `isFeatureEnabled("helmetless")` из того же файла.

Два таких же места остались нетронутыми, оба меняют расчёт, а не показ:
`_getFatiguePenalty` ([actor-sheet.mjs:600](../module/sheets/actor-sheet.mjs))
берёт отсрочку штрафов Усталости у Добывающего мира, а
[actor.mjs:1091](../module/documents/actor.mjs) — прибавку к грузоподъёмности.
Закрывать ли выключателем и их, решается отдельно: это уже правка игрового
расчёта у существующих персонажей.

### 1.5. Реестр источников и `collectRules` ✅

`module/rules/sources.mjs` и `module/rules/collect.mjs`. Пока регистрируем два
источника, самые простые:

```js
registerRuleSource("race",      a => RACES[a.system.race]?.rules ?? []);
registerRuleSource("homeworld", a => HOMEWORLD_BY_KEY[hwKey(a)]?.rules ?? []);
```

Ключ Происхождения лежит на предмете-носителе, а не в `system` актора, и
`hwKey` в `sources.mjs` его оттуда достаёт. Тянуть готовый `actorHomeworldKey` из
[apps/homeworlds.mjs](../module/apps/homeworlds.mjs) нельзя: этот файл работает с
`ui`, `Dialog` и остальным Foundry, и реестр правил перестал бы запускаться в
тестах.

Поле `rules` у данных расы пока не заполнено, источник вернёт пустой массив. Это
нормально, заполнение идёт на этапе 3.

`collectRules(actor, ctx)` собирает всё, отбирает по `matchRule`, снимает
вытесненные через `overrides` и возвращает плоский список. Упавший источник не
роняет сборку: ошибка в консоль, остальные источники отрабатывают.

**Готово, когда:** тест собирает правила у подставного актора из двух подставных
источников и проверяет, что вытеснение по `overrides` работает: правило с
`overrides: ["a"]` убирает из результата правило с `id: "a"`. Сейчас: 13 тестов,
включая взаимное вытеснение и то, что не прошедшее отбор правило ничего не
вытесняет.

## Этап 2. Единый конвейер теста

**Зачем:** появляется одно место, куда подключаются правила. Сейчас таких мест нет:
125 вызовов `1d100` в 30 файлах и ни одного `Hooks.call` во всём проекте.

**Размер:** L. **Риск:** средний, затрагивает боевые расчёты. Атаки на этом этапе
не трогаем.

Перед первым шагом устранена коллизия имён. В предикатах `ctx.target` означал
актора цели, а в матчере ситуативных модификаторов — флаг «бросок нацелен», и на
этом этапе оба контекста сходятся в одном объекте. Переименован предикат:
`targetHasTrait` читает `ctx.targetActor`. Данные не тронуты — `when.target: true`
уже лежит в Особенности Мира Смерти
([homeworlds.mjs](../module/constants/homeworlds.mjs), «Паранойя Выжившего»), и
переименование в них потребовало бы миграции.

### 2.1. Описать конвейер ✅

`module/rules/resolve-test.mjs`, функция `resolveTest(ctx)`. Семь фаз:

| Фаза | Что делает |
| --- | --- |
| 1. Контекст | кто бросает, чем, по кому, вид теста |
| 2. Сбор правил | `collectRules(actor, ctx)` плюс `Hooks.callAll("dbc.collectRules", ctx, bag)` |
| 3. Отбор | по `when`, снятие вытесненных |
| 4. Диалог | ситуативные галочки игроку |
| 5. Бросок | единственное место, где встречается `1d100` |
| 6. Последствия | урон, крит, состояния |
| 7. Карточка | сообщение в чат со списком источников модификаторов |

Правила вмешиваются только на фазах 2 и 3 и ничего не знают ни про интерфейс, ни
про чат. Это условие делает их тестируемыми.

Фаза 2 потребовала разделить `collectRules`: сбор от источников (`gatherRules`) и
отбор (`selectRules`) стали отдельными функциями, а `collectRules` — их
композицией, поэтому прежние вызовы работают без правок. Разделение нужно, чтобы
хук получал список правил **до** отбора: дописанное сторонним модулем правило
просеивается по `when` наравне с остальными.

`Hooks` в тестах не существует, поэтому вызов обёрнут проверкой
`typeof Hooks === "undefined"`. Без этого конвейер тянул бы за собой запуск
Foundry, и фазы 1–3 стало бы нечем проверять.

**Готово, когда:** фазы 1–3 реализованы и покрыты тестами, фазы 4–7 пока вызывают
существующий код листа. Сейчас: 18 тестов в
[test/rules/resolve-test.test.mjs](../test/rules/resolve-test.test.mjs).

### 2.2. Подключить конвейер к тестам навыков ✅

Точки входа найдены:

- [`_rollSkill`](../module/sheets/actor-sheet.mjs) — строка 5218
- [`_showSkillRollDialog`](../module/sheets/actor-sheet.mjs) — строка 5136
- [`_rollCharacteristic`](../module/sheets/actor-sheet.mjs) — строка 5723

Диалог уже собирает модификаторы из двух источников: `_homeworldModsHtml`
(строка 5079) и `_itemRollModsHtml` (строка 5107). Третьим стал
`_ruleRollModsHtml` — он вызывает `resolveTest` и раскладывает его галочки тем же
разметочным блоком. `when` в галочке правила не нужен: отбор прошёл на фазе 3, и
не подходящее актору правило до диалога не доходит. Вместо него в записи лежит
`ruleId`, по которому видно, какое правило дало модификатор.

Точки входа `_rollSkill` и `_rollCharacteristic` правок не потребовали: обе идут
через `_showSkillRollDialog`, и контекст собирается там же, где раньше. Вид теста
у обеих остался `kind: "skill"` — его читает матчер ситуативных модификаторов, и
смена значения убрала бы галочки Особенностей с тестов характеристик. Тест
характеристики отличается от теста навыка отсутствием `ctx.skill`, этого хватает.

Заодно закрыт выключатель подсистемы у источника правил. `_homeworldModsHtml`
проверяет `isFeatureEnabled("homeworlds")` с шага 1.4, а источник `homeworld` в
[sources.mjs](../module/rules/sources.mjs) такой проверки не имел: выключенные
«Происхождения» убрали бы галочки из диалога, но правила Происхождения
продолжали бы действовать. Пока поле `rules` пусто, это ничего не ломало, к этапу

[test/rules/sources.test.mjs](../test/rules/sources.test.mjs).

## Этап 3. Астартес целиком на правилах

**Зачем:** эталон. По этому примеру следующие расы добавляются без участия
программиста. Здесь же впервые проверяется вытеснение `overrides` — механизм, ради

### 3.1. Перевести расовые черты Астартес в правила ✅

Источник: [races.mjs](../module/constants/races.mjs), ключ `astartes`, поле `traits`.
Шесть черт, у трёх уже есть машинные эффекты (`sizeMod`, два `charBonusStat`), у
остальных правило только в тексте.

Текст `benefit` **не удаляем**: он остаётся описанием для игрока. Рядом появилось
поле `rules: ASTARTES_RULES`, а сами правила легли в
[library/astartes.mjs](../module/rules/library/astartes.mjs).

Пять правил на шесть Черт:

- `astartes.size` — `grantValue` в `sizeMod`;
- `astartes.unnatural.strength` и `astartes.unnatural.toughness` — `charBonus` +4;
- `astartes.geneseed` — доступ к талантам Геносемени;
- `astartes.physiology` — лечение и профиль безоружного удара; это не Черта, а
  свойство расы из описания книги, и в `traits` его никогда не было.

Две Черты машинной части не получили, и это осознанно. «Амфибия» перебрасывает
Плавание, а область эффекта различает навык целиком (`skill:athletics`), не
специализацию: переброс всей Атлетики был бы другим правилом. «Проворный» даёт
штраф атакующему, а атаки переходят на конвейер только на шаге 5.2.

`when` у всех пяти пуст: правила приходят от источника `race`
([sources.mjs](../module/rules/sources.mjs)), который уже выбирает их по расе
актора. Вторая проверка в данных разошлась бы с источником при первой правке.

Реестр эффектов пришлось дополнить. Ни один из двенадцати видов не выражал
разрешение («лечится как космодесантник»), а шаг 3.2 состоит именно из них,
поэтому появился `grantFlag` — возможность по имени
([effects.mjs](../module/rules/effects.mjs), раздел «Возможности» в
[rules-format.md](rules-format.md)).

Числа при этом никуда не задвоились. `charBonus` и `grantValue` пока никто не
применяет: до расчёта доходят только `rollBonus` и `penaltyMul` через диалог
броска (шаг 2.2), а остальные виды подключатся вместе с фазами 5–6 конвейера. +4
к Силе на листе по-прежнему даёт Черта-предмет со старым полем `effects`, и снять
её можно будет только тогда, когда правила начнут считать сами. Первое правило
плана: новое живёт рядом со старым.

**Готово, когда:** `test/rules/library/astartes.test.mjs` проверяет, что у
подставного актора расы `astartes` собирается ожидаемый набор правил, включая
`+4` к бонусу Силы и Стойкости и `sizeMod: 1`. Сейчас: 7 тестов.

### 3.2. Убрать проверки расы из листа персонажа ✅

Двадцать одна проверка `system.race === "…"`, из них игровые (а не отрисовочные)
в первую очередь:

- [actor-sheet.mjs:2654–2683](../module/sheets/actor-sheet.mjs) — доступность
  талантов по расе
- [actor-sheet.mjs:4871](../module/sheets/actor-sheet.mjs)
- [actor-sheet.mjs:5318, 5352](../module/sheets/actor-sheet.mjs) — физиология
  Астартес при лечении
- [actor.mjs:930](../module/documents/actor.mjs)
- [utils.mjs:106](../module/helpers/utils.mjs)

Каждая заменяется на запрос к правилам. Проверки, которые управляют только
показом блока в интерфейсе, оставляем: это не игровая логика.

Запрос живёт в [rules/flags.mjs](../module/rules/flags.mjs): `hasRuleFlag(actor,
"healing.astartes")` вместо сравнения расы. Заменены три места про Астартес:
папка талантов «Геносемя» в `_talentGroupLock`, профиль безоружного удара в
`_showAttackDialogNoWeapon` и физиология при лечении — в `_applyHealing` и в
примечании диалога лечения.

Текст замка на папке изменился: было «Нужна раса Астартес», стало «Нужно
Геносемя (раса Астартес)». Причина блокировки теперь и правда возможность, а не
раса, и раса осталась в скобках, чтобы игрок понимал, откуда её взять.

Три проверки оставлены нетронутыми, причины разные:

- [actor.mjs:930](../module/documents/actor.mjs) и
  [utils.mjs:106](../module/helpers/utils.mjs) — про Друкхари, не про Астартес. У
  расы ещё нет библиотеки правил, а `fateTerm` принимает `system`, не актора:
  запрос к правилам требует актора, и это переезд вместе с расой.
- [sheet-helpers.mjs:892](../module/sheets/sheet-helpers.mjs) — `context.isAstartes`
  читают только шаблоны (`header.hbs`, `tab-abilities.hbs`, `tab-notes.hbs`), это
  показ.
- Мастер создания ([actor-sheet.mjs:1901](../module/sheets/actor-sheet.mjs),
  [apps/archetypes.mjs:61](../module/apps/archetypes.mjs)) читает расу из формы
  выбора: актора с этой расой ещё нет, спрашивать правила не у кого.

**Готово, когда:** в перечисленных строках нет сравнений с `"astartes"`, а
поведение листа не изменилось (проверка: персонаж-астартес открывается, лечение
считается как раньше, таланты Легиона доступны). Автоматическая часть — в
[test/rules/flags.test.mjs](../test/rules/flags.test.mjs) (5 тестов) и
[test/sheets/astartes-flags.test.mjs](../test/sheets/astartes-flags.test.mjs)
(5 тестов): у Астартес пассивное лечение по-прежнему считается Отдыхом и даёт те
же 2 Раны, у человека остаётся пассивным и даёт 1. Проверено мутацией: сломанное
имя возможности в данных роняет четыре теста из десяти. Открытие листа и урон
безоружного удара смотрятся руками в Foundry.

### 3.3. Проверить вытеснение на психосилах ✅

Библиотека Либрариума уже помечена как «только на Космодесантников; нужен Астартес»
([psychic-powers-library.mjs:1229](../module/constants/psychic-powers-library.mjs)),

Пара осталась в тесте, в библиотеку не поехала. В содержании системы двух версий

**Готово, когда:** тест на двух подставных акторах показывает по одному
действующему правилу у каждого, и это разные правила. Сейчас:
[test/rules/psychic-overrides.test.mjs](../test/rules/psychic-overrides.test.mjs),

## Этап 4. Контент в данные

**Зачем:** 35 586 строк в [module/constants/](../module/constants/) — это данные
книг внутри кода. Они заливаются в компендиумы при каждом запуске мира, а сами
компендиумы в бинарном LevelDB закоммичены в git (176 файлов). Правка контента
требует программиста, конфликты слияния в бинарнике неразрешимы.

**Размер:** XL. **Риск:** средний. Обратимо: паки пересобираются из JSON.

Важно: содержимое **уже лежит в паках**, залитое при прошлых запусках. Поэтому
переписывать 35 тысяч строк вручную не нужно, их надо извлечь.

**Итог этапа:** содержимое компендиумов лежит в `packs-src/` (5 106 документов
в 30 паках-библиотеках и 11 книг), `packs/` собирается из него — локально
командой, в релизе силами CI, — и в git больше не входит. Наполнение при
запуске мира снято: `warhammer-dbc.mjs` уменьшился с 2 956 строк до 1 420.
Библиотеки в `module/constants/` остались, но данными компендиумов быть
перестали. Протокол сверки содержимого до и после —
[docs/checks/stage-4.md](checks/stage-4.md).

### 4.1. Извлечь существующие паки в JSON ✅

```text
npm i -D @foundryvtt/foundryvtt-cli
```

Скрипт [tools/unpack.mjs](../tools/unpack.mjs) — `npm run packs:unpack`. От
заготовки выше он отличается двумя вещами, и обе нашлись при первом запуске.

**Список паков берётся из `system.json`, а не из папки `packs/`.** В папке лежат
три директории, которых в `system.json` нет: `effects` и `script-library`
(последний удалён за ненадобностью, о чём говорит комментарий в
[item-script.mjs](../module/apps/item-script.mjs)) и `book-homeworlds` —
остаток переименования, живой пак с этим именем лежит в `packs/book-origins`.
Foundry их не загружает, и в сборку они попадать не должны. Заодно `system.json`
даёт тип пака, а он нужен книгам.

**Книги извлекаются в свой формат, а не в формат инструмента Foundry.** У
одиннадцати книжных паков исходник уже был — `packs-src/books/*.json`, по файлу
на книгу, тот же формат читает импорт книг в живом мире
([books.mjs](../module/apps/books.mjs)). Извлечение по документу на файл дало бы
второй экземпляр тех же 18 МБ текста, уже со вставленными ссылками, и две
разные истины на один текст. Поэтому появился
[tools/book-source.mjs](../tools/book-source.mjs): обратное преобразование
документов компендиума в прежний формат исходника.

Оно понадобилось не только ради формата. Прежний JSON от паков отстал, причём
не мелочами: в паках лежит вычитанный руками текст, а в JSON — сырая выгрузка
из PDF, где двухколоночная вёрстка перемешана построчно, а в разделе «Стартовые
характеристики» вместо правил оказалось затёкшее «Содержание». В `book-core`
есть и глава «IX. FOUNDRY», которой в PDF нет вовсе. Собери книги из прежнего
JSON — и игроки получили бы текст хуже нынешнего. Источник истины у книг —
то, что лежит в паке, и извлечение это в исходник вернуло.

Ссылки `@UUID` при извлечении снимаются до подписи: их расставляет сборка, и
сохранённая ссылка попала бы внутрь новой при следующей.

**Готово, когда:** в `packs-src/` лежат JSON-файлы по всем паками, число записей
совпадает с числом документов в компендиумах Foundry. Сейчас: 5 106 документов
в 30 паках-библиотеках плюс 106 глав и 1 570 разделов в 11 книгах, полная
таблица — [docs/checks/stage-4.md](checks/stage-4.md).

### 4.2. Собирать паки в CI ✅

[tools/pack.mjs](../tools/pack.mjs) — `npm run packs:build`. Библиотеки
собираются из `packs-src/<имя>/` как есть, книги — из `packs-src/books/` через
[tools/book-docs.mjs](../tools/book-docs.mjs), и только после библиотек: ссылки
`@UUID` в тексте книги указывают на предметы, поэтому сначала нужны их
идентификаторы.

Ссылки расставляются тем же кодом, что и в живом мире. Из
[books.mjs](../module/apps/books.mjs) выделена Foundry-независимая половина
сборщика индекса (`indexNames`), а `linkify` и так была чистой функцией.
Разойдись эти две дороги — CI собирал бы книги иначе, чем мир.

Идентификаторы глав и страниц книг выводятся из книги и номера главы
(`stableId`), а не берутся случайными: пересборка не должна менять ссылки на
страницы книг. Проверено, что ссылаться на них извне сейчас никто не ссылается,
но менять их на каждой сборке всё равно нельзя.

Шаг сборки добавлен в [release.yml](../.github/workflows/release.yml) перед
созданием архива, вместе с установкой зависимостей: в релизном workflow Node
раньше не было вовсе.

⚠️ Запись `packs-src/**` убрана из `paths-ignore` — иначе правки контента молча
не попали бы ни в один релиз.

В [check.yml](../.github/workflows/check.yml) добавлена проверка круговорота:
собрать компендиумы, извлечь обратно, `git diff --exit-code -- packs-src`.
Расхождение хоть на байт — красный пул-реквест. Это самая сильная из проверок
этапа: она ловит и потерю содержимого при сборке, и расхождение двух
инструментов между собой.

**Готово, когда:** собранная в CI система устанавливается в Foundry и компендиумы
открываются с тем же содержимым. Автоматическая часть: содержимое сверено до и
после переезда — библиотеки совпали дословно, книги совпали по главам, разделам,
номерам страниц PDF и тексту ([docs/checks/stage-4.md](checks/stage-4.md)).
Установка архива в Foundry смотрится руками на первом релизе.

### 4.3. Убрать LevelDB из git ✅

`packs/` ушла в [.gitignore](../.gitignore), 178 файлов удалены из индекса
(`git rm -r --cached packs`). Сборка их восстанавливает.

Из [.gitattributes](../.gitattributes) убрано правило `packs/** binary`: оно
описывало сравнение файлов, которых в git больше нет.

После клона репозитория `npm run packs:build` нужно выполнить один раз, иначе

пака целиком, поэтому правки, сделанные в Foundry и не снятые через
`npm run packs:unpack`, она потеряет.

**Готово, когда:** `git ls-files packs` пусто, а установка из релиза работает.
Сейчас: `git ls-files packs` пусто; установка проверяется на первом релизе.

### 4.4. Удалить наполнение при запуске мира ✅

Наполнение оказалось не «около двадцати функций», а девятнадцать хуков
`ready` подряд плюс движок синхронизации `_fillModLibrary` — 1 501 строка.
Удалялись не по одной: проверка «запустить мир и посмотреть» на девятнадцать
подходов не масштабируется, а по одной удалять их всё равно нельзя — они делят
общие таблицы полей и помощников по папкам.

Вместо этого наполнение просимулировано на содержимом `packs-src` до удаления:
по фактическим спискам синхронизируемых полей каждого хука и с тем же
сравнением значений, что в коде. Итог — таблица в
[docs/checks/stage-4.md](checks/stage-4.md): добавить нечего, иконки не
меняются, папки чистить нечего; из записей остаются 1 074 перезаписи `effects`
теми же значениями, 178 полей, равных значению по умолчанию, 24 перезаписи
текста и 14 переносов по папкам.

Два вывода из симуляции изменили сам шаг.

**`bookSource` пришлось перенести в данные.** Наполнение писало это поле в
компендиум из библиотек, а в паке его не было вовсе у 1 448 предметов: в схеме
оно появилось позже самих записей. Поле видимое — «книга-источник» на листе
предмета, — поэтому оно перенесено в `packs-src` отдельным коммитом до
удаления. Иначе свежая установка получила бы 1 448 предметов с пустой строкой.

**24 расхождения в тексте оставлены за паком.** Там, где выжимка Черты в паке
полнее («Размер: +1 (крупнее человека)» против «Размер: +1»), наполнение
затирало пак кодом. Игроки видят версию из пака, и после этапа 4 она — источник
истины.

В удаляемый диапазон попал `initPackCaches()` — вызов на верхнем уровне, к
наполнению не относящийся: он строит кэш Происхождений и Предсказаний для
дропдаунов в шапке листа. Возвращён на место. Проверка была механической:
перечислить все конструкции колонки 0 в удаляемых диапазонах и убедиться, что
всё остальное — хуки наполнения, таблицы полей и помощники.

Осталось работать: разблокировка компендиумов по настройке, миграция
`system.effects` → `ActiveEffect` (чинит предметы на акторах мира, а в паках все
2 577 предметов уже с флагом), типы `divideUp`/`divideDown` и двупрофильные
предметы. Последним нужны `GEAR_LIBRARY`, `TOOLS_LIBRARY` и `IMPLANT_LIBRARY`,
поэтому три импорта из двадцати девяти остались.

Текст настройки «Защита правок в библиотеках» переписан: переписывать правки
при запуске больше нечему, настройка только разблокирует компендиумы. Ключ
`protectCompendiumEdits` оставлен прежним, чтобы у существующих миров не
сбросился выбор.

Файлы в `module/constants/` не удалялись: библиотеки читают пикеры, мастер
создания и расчёты. Данными компендиумов они быть перестали, и это отдельная
задача — разобрать, что там осталось живого.

**Готово, когда:** в `warhammer-dbc.mjs` нет функций наполнения, мир запускается
быстрее, компендиумы на месте, файл уменьшился примерно вдвое. Сейчас: 2 956
строк → 1 420, наполнения нет, симуляция показывает, что содержимое
компендиумов не меняется. Запуск мира и открытие компендиумов смотрятся руками.

### 5.1. `TypeDataModel` вместо `template.json` (L) — идёт

[template.json](../template.json) на 53 КБ описывает 10 типов акторов и 35 типов
предметов без валидации и без `migrateData`. Опечатка в пути поля проявляется как
тихий `undefined` в расчётах.

Переводим по одному типу. Классы лежат в [module/data/](../module/data/), список
переведённых — в [data/index.mjs](../module/data/index.mjs), оттуда он попадает в
`CONFIG.Item.dataModels` в хуке `init`. Запись типа в `template.json`
опустошается в том же коммите (`"trait": {}`): зарегистрированный тип её больше
не читает, а два описания одной схемы разъедутся при первой правке. Сам тип из
списка `types` не убирается — им он и объявлен.

Переведены три типа предмета: `weaponProperty`, `aspiration` (простые, по плану)
и `trait` — ради `migrateData`, которому нужны данные прошлого формата.

Перевод типа проверяется двумя вопросами
([test/data/item-schemas.test.mjs](../test/data/item-schemas.test.mjs)):

- **умолчания** — новый предмет получает ровно то, что раздавал `template.json`;
- **сохранность** — каждый документ типа из `packs-src` проходит через схему без
  потерь. Поле, забытое в `defineSchema()`, Foundry не сохранит, и данные книги
  исчезнут при первой правке предмета в игре.

Вторая проверка сразу нашла поле мимо схемы: у Черт есть `requirement`, которого
в `template.json` не было никогда. Оно пустое во всех 274 записях пака, но
читается пикером Черт (`_openItemPicker` показывает требование и подсвечивает
невыполненное), поэтому переехало в схему, а не пропало.

Миграция нашлась там же, где и требовал план, — на настоящих данных. Одиночный
бонус к Бонусу характеристики лежит двумя полями (`effects.charBonusStat` +
`effects.charBonusValue`), а поздние Черты пишут тот же бонус списком
`charBonuses`. Оба формата тянутся через расчёт актора и через перенос механики
в `ActiveEffect`; `TraitData.migrateData` оставляет один — список. Проверяется не
форма записи, а равенство результата: `legacyEffectsToChanges` даёт одинаковые
`changes` до и после миграции
([test/data/trait-migration.test.mjs](../test/data/trait-migration.test.mjs), 6
тестов, три Черты пака прошлого формата). Проверено мутацией: и потерянный
перенос, и оставленные старые поля роняют по три теста.

Поле `effects` у Черты объявлено свободным объектом, а не разобранной схемой.
Механика Черт переезжает в `ActiveEffect` (`_migrateItemEffects`), и перечислять
её ключи схемой значило бы закреплять формат, который снимается.

Тестам понадобились поля Foundry, поэтому заглушка
([test/support/foundry-stub.mjs](../test/support/foundry-stub.mjs)) получила
`StringField`, `NumberField`, `BooleanField`, `ObjectField` и `TypeDataModel` с
тем же порядком инициализации: `migrateData`, потом очистка полей. Валидацию
заглушка не изображает — недопустимое значение поля с `choices` она пропустит, а
настоящий Foundry поднимет ошибку. Поэтому тесты спрашивают про умолчания и
сохранность данных, а не про поведение на заведомо неверных значениях: иначе
проверялась бы заглушка.

**Готово, когда:** тип переведён, старые миры открываются, `migrateData`
покрыт тестом на данных прошлого формата. Сейчас: 3 типа предмета из 35, 13
тестов; открытие мира со старыми предметами смотрится руками в Foundry.
Осталось 32 типа предмета и 10 типов актора, `character` последним.

### 5.2. Атаки на общий конвейер (L) ✅

[`_executeAttackRoll`](../module/combat/attack.mjs) была 666 строк одной
функцией. Разобрана на фазы конвейера из этапа 2; осталось 565 строк
оркестровки, а расчёты уехали в два файла, которые проверяются без Foundry:

- [attack-weapon.mjs](../module/combat/attack-weapon.mjs) — фаза 1 со стороны
  оружия: профиль, хват, боеприпас, выключенное оружие;
- [attack-outcome.mjs](../module/combat/attack-outcome.mjs) — фаза 6: число
  попаданий, место попадания, Пробитие, формула урона, добавочные кубы;
- [attack-threshold.mjs](../module/combat/attack-threshold.mjs) — фаза 4:
  сложение модификаторов и ополовинивание штрафа.

Разбор шёл под сетью безопасности: восемь боевых сценариев плана были записаны
тестами **до** первой правки и не менялись вместе с ней
([attack-parity.test.mjs](../test/combat/attack-parity.test.mjs)). Тестам
понадобился честный бросок, поэтому заглушка Foundry научилась разбирать формулы
и отдавать заданную очередь кубов — узко, только `NdM`, `min`, `kh` и целые
слагаемые: формула вне набора роняет тест, а не считается молча неправильно.

Правила подключены к атаке так же, как к броску навыка на шаге 2.2: вид теста
`attack`, области эффектов `attack`, `weapon:melee`, `weapon:ranged` и
`weapon:<класс>`. Метательное считается рукопашным — как и в самой атаке;
разойдись эти два места, одно правило действовало бы в диалоге иначе, чем в
броске. Область `char:` в атаку намеренно не подхватывается: «+10 к тестам
Оружейного Мастерства» и «+10 ко всем ударам» — два разных правила книги.

Заодно закрыт долг этапа 3. Черта «Проворный» даёт штраф не носителю, а тому,
кто по нему бьёт, и есть у четырёх рас, поэтому правило одно на всех и лежит в
[library/core.mjs](../module/rules/library/core.mjs), а отбирается по Черте у
цели. Числа в данных быть не может — штраф равен Бонусу Ловкости конкретной
цели, — и формат правил получил поле `valueFrom`
([rules-format.md](rules-format.md)). Вместе с ним появился источник `core`:
правила основной книги приходят каждому актору и отбираются условием `when`.

Три вещи разбор не тронул и не должен был. Хват «в полтора» передаёт в атаку
флаг `gripSbHalf`, а атака его не читает: половинный Бонус Силы не применяется.
Расхождение старше этого шага, и его починка — правка игрового расчёта у
существующих персонажей, то есть отдельная задача. Психосилы на конвейер не
переводились, область `power:` по-прежнему ни с чем не совпадает. Сборка
карточки чата осталась в `attack.mjs`: это фаза 7, и её выделение имеет смысл
вместе с разбором листа (шаг 5.3), а не до него.

**Готово, когда:** таблица сверки, как в шаге 2.3, но на боевых сценариях:
рукопашная, стрельба, очередь, выключенное оружие, профиль оружия, боеприпас со
свойствами, щит, прицеливание. Сейчас:
[docs/checks/stage-5.md](checks/stage-5.md), тринадцать боевых строк и восемь
строк про правила, все автоматические. Проверено мутацией: потерянное сложение
галочек правил и сбитый счёт попаданий в очереди роняют тесты. Руками в Foundry
остаётся показ: диалог атаки открывается, блок «Правила» на месте, карточка
выглядит как раньше.

### 5.3. Разбор листа персонажа (XL) — идёт

7 297 строк, 173 метода, 562 ветвления. Вкладка за вкладкой в отдельные модули:
хирургия, мутации, мастер создания, генетика, пикеры предметов, гемункул.

делать в этом проекте.

Приём один на все выносы, и он же — защита от «переехало, но поехало»:

1. Тест пишется **до** правки и проверяет подсистему через лист, как она
   работает сейчас.
2. Подсистема переезжает в модуль. Функции принимают **актора**, а не лист:

  купленных талантов, записи Групп Навыков (ранг с авто-ценой, ручная цена,
  своя Характеристика, переименование и удаление через меню ПКМ) и список
  Талантов в Развитии. Накопительные цены (`charImpCost`, `skillCumCost`,
  стр. 23-24) тоже здесь: соседние секции листа зовут их обёртками
  ([тест](../test/sheets/advance-tab.test.mjs), 15 тестов);
- [context-menu.mjs](../module/sheets/context-menu.mjs) — меню по правой кнопке:
  общий конструктор пунктов и меню строки предмета (открыть лист / удалить).
  Меню групповых навыков и снятие меню при скролле «Развития» построены тем же
  конструктором из `tabs/advance.mjs`
  ([тест](../test/sheets/context-menu.test.mjs), 5 тестов);
- [tabs/wounds.mjs](../module/sheets/tabs/wounds.mjs) — общий расчёт лечения и
  непоглощаемого урона в Раны. Им пользуются Лечение, Очки Боли, препараты и
  вынесенные психосилы;
- [apps/creation.mjs](../module/apps/creation.mjs) — Мастер создания персонажа:
  окно с выбором Раса → Субраса → Мировоззрение → Архетип и раскидкой бросков
  «Генерации», применение выбора (характеристики только в пустые поля, Раны и
  Влияние по формулам архетипа, геносемя и культура легиона), бесплатная выдача
  стартовых навыков с разбором строк книг и отключённая пока выдача снаряжения.
  Черты, стартовые таланты, органы Геносемени и тема листа остались на листе и
  приходят в модуль колбэками: их зовут и кнопки «Применить расу»/«Применить
  легион» ([тест](../test/apps/creation.test.mjs), 29 тестов). Общий разбор
  строк книг по запятым верхнего уровня переехал в
  [helpers/utils.mjs](../module/helpers/utils.mjs) — его зовут и выдача навыков,
  и стартовые таланты.

Проверено мутацией: снятое ограничение сдвига по Бонусу Влияния и неотмеченный
перерасход пула Идеалов роняют по тесту. Так же проверены последние выносы:
снятое ограничение стадии 0…3 у Жизненных потребностей, пункт меню, который
перестал закрывать меню, и крестик состояния, оставивший счётчик ненулевым,
роняют тесты вкладки ТЕЛО, контекстного меню и Состояний.

На органах Геносемени мутация сначала прошла незамеченной: проверка состояний
шла одним органом по цепочке, и флаг от прошлого перехода прикрывал пропажу
нового. Каждое состояние теперь проверяется на свежем органе — обе мутации
(«сломанный больше не вживлён», «вживление не снимает поломку») роняют тест.

Заглушке Foundry понадобилась выдача предметов: тест мутаций проверяет не
разметку диалога, а запись, которая легла на лист, поэтому подставной актор
запоминает `createEmbeddedDocuments`.

Вкладка РАЗВИТИЕ проверена пятью мутациями: цена, посчитанная без выданного
архетипом уровня, потерянный `alwaysAlly` у Общих знаний и Ремесла, ранг без
пересчёта цены, удаление таланта в обход подтверждения и пересчёт, залезший на
выданные таланты, — каждая роняет свой тест. Подставной актор здесь применяет
обновления по плоскому пути, как настоящий документ: пересчёт цен читает
склонности сразу после их записи, и на записывающей-в-пустоту заглушке проверка
была бы слепой.

Мастер создания проверен двумя связками мутаций. Разбор строк книг: запятая
внутри имени специализации, которая начала резать «Warp, Daemons and Psykers»,
потерянная названная специализация рядом с «любое N», повторный прогон, плодящий
свободные слоты, сверка слотов по `wild` вместо `wildSlot`, выданный ранг,
понижающий купленный, съеденное предупреждение о нераспознанной записи и
проигнорированный выбор снаряжения. Применение: затёртая заполненная
характеристика, переброшенные готовые Раны, непомеченный архетип-псайкер,
потерянные таланты культуры легиона, Астартес без органов Геносемени,
неприбавленная раскидка бросков и Мировоззрение, потерянное по дороге из формы.
Каждая роняет свой тест.

**Готово, когда:** в `actor-sheet.mjs` меньше 2 000 строк, а вынесенные модули не
импортируют его обратно. Сейчас: 2 798 строк, обратных импортов нет. Открытие

## Этап 6. ApplicationV2

**Зачем:** все листы наследуют `foundry.appv1.sheets.ActorSheet` и работают через
`getData()`, `activateListeners(html)` и jQuery: 357 вызовов `html.find()` в одном
листе персонажа. ApplicationV1 в v13 помечен устаревшим и будет удалён.

**Размер:** XL. **Риск:** высокий. Делать последним, по одному листу.

Foundry v13 позволяет держать V1 и V2 одновременно, поэтому большого перехода не
будет. Порядок: от простого к сложному. `horde-sheet.mjs` (313 строк, 9 вызовов
`html.find()`) → `daemon-sheet.mjs` → `vehicle-sheet.mjs` → … → `actor-sheet.mjs`
последним, уже после разбора на модули.

Целевые базовые классы:

```js
const { HandlebarsApplicationMixin } = foundry.applications.api;
const { ActorSheetV2 }               = foundry.applications.sheets;

class WarhammerHordeSheet extends HandlebarsApplicationMixin(ActorSheetV2) { }
```

Листы предметов наследуют `DocumentSheetV2`. В проекте уже есть один V2-класс как
образец: [active-effect-config.mjs](../module/sheets/active-effect-config.mjs).

**Готово, когда:** лист переведён, все кнопки и поля работают, в файле нет
`html.find`, `getData` и `activateListeners`.

## Чего делать не стоит

**Не переписывать систему с нуля.** Объём правил здесь больше, чем в большинстве
коммерческих систем Foundry, и он выверен по книгам. Переписывание займёт годы и
потеряет содержание.

**Не решать вариативность через `kind: "script"`.** Свободный JS на предмете
([mechanics.mjs](../module/apps/mechanics.mjs), запись «Код») снимает задачу
сегодня и возвращает её через полгода: правила снова станут кодом, только теперь
размазанным по сотням предметов, вне git и вне тестов. Скрипт остаётся аварийным
выходом.

**Не начинать с интерфейса.** 16 681 строка CSS и перевод на ApplicationV2
выглядят понятной работой с видимым результатом, но пока правила зашиты в лист,
переделка интерфейса тащит их за собой и делается дважды. Поэтому этап 6 последний.

**Не вводить предикат там, где хватает значения.** Если у эльдар просто другое
число, это поле в данных расы. Предикаты нужны, когда правило зависит от
обстоятельств броска.

**Не удалять текст `benefit`.** Машинные правила добавляются рядом с ним, а не
вместо. Игрок читает описание, система применяет эффекты, и расхождение между ними
ловится тестом.
