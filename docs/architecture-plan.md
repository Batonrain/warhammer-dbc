# План архитектурных исправлений

Цель: сделать так, чтобы вариативные правила (раса, фракция, архетип, дисциплина)
описывались данными, а не кодом. Побочный результат: систему станет возможно
проверять автотестами и править контент без программиста.

## Как пользоваться планом

Этапы идут по порядку. Каждый следующий опирается на предыдущий, перескакивать не
стоит: этапы 4–6 без реестра правил из этапа 1 придётся делать дважды.

Внутри этапа шаги пронумерованы. У каждого есть строка **Готово, когда** —
проверяемый признак завершённости. Если признак не выполняется, шаг не закрыт,
даже когда код написан.

Отметки размера: **S** до часа, **M** до дня, **L** несколько дней, **XL** недели.

## Три правила на весь план

1. **Новое живёт рядом со старым.** Ни один этап не начинается с удаления
   работающего кода. Сначала новый механизм работает параллельно, потом старый
   снимается по частям.
2. **Ветка на этап, не на весь план.** Ветвление длиной в месяц не сольётся:
   [actor-sheet.mjs](../module/sheets/actor-sheet.mjs) правят все.
3. **Каждый шаг проверяем.** Пока правила зашиты в интерфейс, проверка ручная:
   открыть лист, бросить кубик, сравнить число. Начиная с этапа 1 появляются тесты,
   и ручную проверку заменяет `npm test`.

**Готово, когда:** `npm install` проходит, `node_modules` не появляется в
`git status` (уже в [.gitignore](../.gitignore)).

## Этап 1. Реестр правил

**Зачем:** появляется единственное место, где живут условия и эффекты. Существующий
код не меняется, только получает новую опору.

**Размер:** L. **Риск:** нет, старые пути исполнения не затрагиваются.

Формат записи правила описан отдельно: [rules-format.md](rules-format.md). Этот
документ читается до начала шага 1.2.

### 1.1. Завести папку `module/rules/` ✅

Файлы-заготовки, пока пустые:

```text
module/rules/
  predicates.mjs      // реестр условий
  effects.mjs         // реестр видов эффектов
  sources.mjs         // реестр источников правил
  collect.mjs         // matchRule + collectRules(actor, ctx)
  match-context.mjs   // матчер контекста броска, приехал на шаге 1.4
  library/            // сами правила по книгам
    core.mjs
    astartes.mjs
    aeldari.mjs
```

`effects.mjs` и три файла библиотеки остаются заготовками: применение эффектов —
этап 2, наполнение библиотеки — этап 3. `effects.mjs` уже держит перечень
известных `kind` и обязательных полей, чтобы таблица из
[rules-format.md](rules-format.md) жила в одном месте с кодом.

**Готово, когда:** папка создана, файлы импортируются друг из друга без ошибок,
`npm run lint` чистый. Проверяется тестом `test/rules/scaffold.test.mjs`.

### 1.2. Реестр предикатов ✅

`module/rules/predicates.mjs`. Каждый предикат — чистая функция
`(actor, ctx, value) => boolean`. Ни обращений к `game`, ни к интерфейсу: это
условие для теста в первую очередь.

Начать с восьми, которых хватает на существующий контент:
`race`, `subrace`, `sizeMax`, `hasTalent`, `hasTrait`, `charMin`, `weaponClass`,
`targetHasTrait`. Точные подписи в [rules-format.md](rules-format.md).

Три места, где реализация уточнила справочник (там он уже поправлен):

- `sizeMax` смотрит на итоговый Размер, а не на одно поле. У актора базовый
  Размер лежит в `system.size`, вклад Черт — в `system.sizeMod`, сумма — в
  `system.sizeTotal` ([actor.mjs:1162](../module/documents/actor.mjs)). Предикат
  берёт `sizeTotal`, а при его отсутствии складывает сам: у подставного актора в
  тесте посчитанного поля нет.
- Список в `hasTalent` и `hasTrait` означает «и», а не «или». Правило с
  альтернативами записывается двумя правилами, а требование двух Талантов сразу
  иначе не выразить.
- Оба предиката ищут и по Талантам, и по Чертам, и сравнивают имя по любой
  половине двуязычного названия. Так же ведёт себя разборщик требований талантов
  ([talent-requirements.mjs:199](../module/constants/talent-requirements.mjs)).

**Готово, когда:** `test/rules/predicates.test.mjs` проверяет каждый предикат на
подставном объекте актора (обычный литерал `{ system: { race: "astartes" } }`,
никакого Foundry), все тесты зелёные. Сейчас: 26 тестов.

### 1.3. Функция отбора `matchRule` ✅

Одна функция: правило подходит контексту, если **все** его условия истинны.
Неизвестный ключ условия — ошибка в консоль и `false`, чтобы опечатка в данных не
проходила молча. Живёт в `collect.mjs`: оттуда её импортирует пример проверки
правила в [rules-format.md](rules-format.md).

Под это же правило попадают условия, описанные в справочнике, но ещё не
реализованные (`alignment`, `sizeMin`, `psyRatingMin`, `discipline`): пока
предиката нет, правило с таким условием не действует и жалуется в консоль.

**Готово, когда:** тест проверяет три случая: все условия истинны, одно ложно,
ключ условия неизвестен.

### 1.4. Переселить `matchesContext` из контентного файла ✅

Сейчас общий матчер лежит в
[homeworlds.mjs:424](../module/constants/homeworlds.mjs) и импортируется листом
персонажа: контентный файл раздаёт механизм, это перевёрнутая зависимость.

1. Перенести тело `matchesContext` в `module/rules/match-context.mjs`.
2. В `homeworlds.mjs` оставить реэкспорт. Функция там ещё и вызывается
   (`homeworldRollMods`), поэтому не `export … from`, а импорт и реэкспорт:

   ```js
   import { matchesContext } from "../rules/match-context.mjs";
   export { matchesContext };
   ```

   Так [actor-sheet.mjs:64](../module/sheets/actor-sheet.mjs) продолжает работать
   без правок.
3. Накрыть перенесённую функцию тестами: контексты навыка, характеристики,
   специализации и флаговые (`suppression`, `single`, `target`).

**Готово, когда:** тесты зелёные, лист персонажа открывается, галочки Особенности
Происхождения появляются в диалоге броска навыка как раньше. Тестами закрыто
и то, что реэкспорт указывает на ту же функцию, и отбор Особенностей через
`homeworldRollMods`; открытие листа проверяется руками в Foundry.

Подсистема называется «Происхождения»
([features.mjs](../module/constants/features.mjs), ключ `homeworlds`), и так же
она подписана в шапке листа. «Родной мир» — название книги-источника, в
интерфейс оно не выходит. В новых файлах пишем «Происхождение»; технические
имена (`homeworld` как тип предмета, `homeworlds` как ключ настройки) остаются
прежними, их переименование — отдельная задача с миграцией данных.

При проверке этого пути нашлась течь выключателя. `homeworlds` выключен, а
галочки Особенности в диалоге броска остаются: выбор из шапки листа пропадает
(`homeworldSheetContext` начинается с `isFeatureEnabled`), а
[`_homeworldModsHtml`](../module/sheets/actor-sheet.mjs) такой проверки не имел.
Добавлена — по образцу `isFeatureEnabled("helmetless")` из того же файла.

Два таких же места остались нетронутыми, оба меняют расчёт, а не показ:
`_getFatiguePenalty` ([actor-sheet.mjs:600](../module/sheets/actor-sheet.mjs))
берёт отсрочку штрафов Усталости у Добывающего мира, а
[actor.mjs:1091](../module/documents/actor.mjs) — прибавку к грузоподъёмности.
Закрывать ли выключателем и их, решается отдельно: это уже правка игрового
расчёта у существующих персонажей.

### 1.5. Реестр источников и `collectRules` ✅

`module/rules/sources.mjs` и `module/rules/collect.mjs`. Пока регистрируем два
источника, самые простые:

```js
registerRuleSource("race",      a => RACES[a.system.race]?.rules ?? []);
registerRuleSource("homeworld", a => HOMEWORLD_BY_KEY[hwKey(a)]?.rules ?? []);
```

Ключ Происхождения лежит на предмете-носителе, а не в `system` актора, и
`hwKey` в `sources.mjs` его оттуда достаёт. Тянуть готовый `actorHomeworldKey` из
[apps/homeworlds.mjs](../module/apps/homeworlds.mjs) нельзя: этот файл работает с
`ui`, `Dialog` и остальным Foundry, и реестр правил перестал бы запускаться в
тестах.

Поле `rules` у данных расы пока не заполнено, источник вернёт пустой массив. Это
нормально, заполнение идёт на этапе 3.

`collectRules(actor, ctx)` собирает всё, отбирает по `matchRule`, снимает
вытесненные через `overrides` и возвращает плоский список. Упавший источник не
роняет сборку: ошибка в консоль, остальные источники отрабатывают.

**Готово, когда:** тест собирает правила у подставного актора из двух подставных
источников и проверяет, что вытеснение по `overrides` работает: правило с
`overrides: ["a"]` убирает из результата правило с `id: "a"`. Сейчас: 13 тестов,
включая взаимное вытеснение и то, что не прошедшее отбор правило ничего не
вытесняет.

## Этап 2. Единый конвейер теста

**Зачем:** появляется одно место, куда подключаются правила. Сейчас таких мест нет:
125 вызовов `1d100` в 30 файлах и ни одного `Hooks.call` во всём проекте.

**Размер:** L. **Риск:** средний, затрагивает боевые расчёты. Атаки на этом этапе
не трогаем.

### 2.1. Описать конвейер

`module/rules/resolve-test.mjs`, функция `resolveTest(ctx)`. Семь фаз:

| Фаза | Что делает |
| --- | --- |
| 1. Контекст | кто бросает, чем, по кому, вид теста |
| 2. Сбор правил | `collectRules(actor, ctx)` плюс `Hooks.callAll("dbc.collectRules", ctx, bag)` |
| 3. Отбор | по `when`, снятие вытесненных |
| 4. Диалог | ситуативные галочки игроку |
| 5. Бросок | единственное место, где встречается `1d100` |
| 6. Последствия | урон, крит, состояния |
| 7. Карточка | сообщение в чат со списком источников модификаторов |

Правила вмешиваются только на фазах 2 и 3 и ничего не знают ни про интерфейс, ни
про чат. Это условие делает их тестируемыми.

**Готово, когда:** фазы 1–3 реализованы и покрыты тестами, фазы 4–7 пока вызывают
существующий код листа.

### 2.2. Подключить конвейер к тестам навыков

**Готово, когда:** галочки от правил появляются в диалоге броска рядом с уже

## Этап 3. Астартес целиком на правилах

**Зачем:** эталон. По этому примеру следующие расы добавляются без участия

**Размер:** L. **Риск:** средний, но обратимый: старые данные расы остаются на
месте до конца этапа.

### 3.1. Перевести расовые черты Астартес в правила

Источник: [races.mjs](../module/constants/races.mjs), ключ `astartes`, поле `traits`.
Шесть черт, у трёх уже есть машинные эффекты (`sizeMod`, два `charBonusStat`), у

Текст `benefit` **не удаляем**: он остаётся описанием для игрока. Рядом появляется

**Готово, когда:** `test/rules/library/astartes.test.mjs` проверяет, что у

### 3.2. Убрать проверки расы из листа персонажа

Двадцать одна проверка `system.race === "…"`, из них игровые (а не отрисовочные)
в первую очередь:

- [actor-sheet.mjs:2654–2683](../module/sheets/actor-sheet.mjs) — доступность
  талантов по расе
- [actor-sheet.mjs:4871](../module/sheets/actor-sheet.mjs)

## Этап 4. Контент в данные

**Зачем:** 35 586 строк в [module/constants/](../module/constants/) — это данные
книг внутри кода. Они заливаются в компендиумы при каждом запуске мира, а сами
компендиумы в бинарном LevelDB закоммичены в git (176 файлов). Правка контента
требует программиста, конфликты слияния в бинарнике неразрешимы.

**Размер:** XL. **Риск:** средний. Обратимо: паки пересобираются из JSON.

Важно: содержимое **уже лежит в паках**, залитое при прошлых запусках. Поэтому
переписывать 35 тысяч строк вручную не нужно, их надо извлечь.

### 4.1. Извлечь существующие паки в JSON

```text
npm i -D @foundryvtt/foundryvtt-cli
```

Скрипт `tools/unpack.mjs`:

```js
import { extractPack } from "@foundryvtt/foundryvtt-cli";
import { readdirSync } from "node:fs";

for (const name of readdirSync("packs", { withFileTypes: true })
                     .filter(d => d.isDirectory()).map(d => d.name)) {
  await extractPack(`packs/${name}`, `packs-src/${name}`,
                    { folders: true, log: true });
}
```

**Готово, когда:** в `packs-src/` лежат JSON-файлы по всем паками, число записей
совпадает с числом документов в компендиумах Foundry.

### 4.2. Собирать паки в CI

Скрипт `tools/pack.mjs` симметричен предыдущему, вызывает `compilePack`. Шаг сборки
добавляется в [release.yml](../.github/workflows/release.yml) **перед** созданием
архива.

⚠️ Здесь же убрать `packs-src/**` из `paths-ignore`. Сейчас эта запись стоит верно:
папка черновая, и правки в ней релиз не заслуживают. После шага 4.1 `packs-src/`
становится источником всего контента, и забытая строка приведёт к тому, что правки
контента молча не попадут ни в один релиз.

**Готово, когда:** собранная в CI система устанавливается в Foundry и компендиумы
открываются с тем же содержимым.

### 4.3. Убрать LevelDB из git

`packs/**` уходит в [.gitignore](../.gitignore), файлы удаляются из индекса
(`git rm -r --cached packs`). Сборка их восстанавливает.

**Готово, когда:** `git ls-files packs` пусто, а установка из релиза работает.

### 4.4. Удалить наполнение при запуске мира

Около двадцати функций в [warhammer-dbc.mjs](../warhammer-dbc.mjs), строки
1107–2775, и импорты `*_LIBRARY` в шапке файла. Удаляются по одной, каждая
проверяется отдельным запуском мира.

**Готово, когда:** в `warhammer-dbc.mjs` нет функций наполнения, мир запускается
быстрее, компендиумы на месте, файл уменьшился примерно вдвое.

## Этап 6. ApplicationV2

**Зачем:** все листы наследуют `foundry.appv1.sheets.ActorSheet` и работают через
`getData()`, `activateListeners(html)` и jQuery: 357 вызовов `html.find()` в одном
листе персонажа. ApplicationV1 в v13 помечен устаревшим и будет удалён.

**Размер:** XL. **Риск:** высокий. Делать последним, по одному листу.

Foundry v13 позволяет держать V1 и V2 одновременно, поэтому большого перехода не
будет. Порядок: от простого к сложному. `horde-sheet.mjs` (313 строк, 9 вызовов
`html.find()`) → `daemon-sheet.mjs` → `vehicle-sheet.mjs` → … → `actor-sheet.mjs`
последним, уже после разбора на модули.

Целевые базовые классы:

```js
const { HandlebarsApplicationMixin } = foundry.applications.api;
const { ActorSheetV2 }               = foundry.applications.sheets;

class WarhammerHordeSheet extends HandlebarsApplicationMixin(ActorSheetV2) { }
```

Листы предметов наследуют `DocumentSheetV2`. В проекте уже есть один V2-класс как
образец: [active-effect-config.mjs](../module/sheets/active-effect-config.mjs).

**Готово, когда:** лист переведён, все кнопки и поля работают, в файле нет
`html.find`, `getData` и `activateListeners`.

## Чего делать не стоит

**Не переписывать систему с нуля.** Объём правил здесь больше, чем в большинстве
коммерческих систем Foundry, и он выверен по книгам. Переписывание займёт годы и
потеряет содержание.

**Не решать вариативность через `kind: "script"`.** Свободный JS на предмете
([mechanics.mjs](../module/apps/mechanics.mjs), запись «Код») снимает задачу
сегодня и возвращает её через полгода: правила снова станут кодом, только теперь
размазанным по сотням предметов, вне git и вне тестов. Скрипт остаётся аварийным
выходом.

**Не начинать с интерфейса.** 16 681 строка CSS и перевод на ApplicationV2
выглядят понятной работой с видимым результатом, но пока правила зашиты в лист,
переделка интерфейса тащит их за собой и делается дважды. Поэтому этап 6 последний.

**Не вводить предикат там, где хватает значения.** Если у эльдар просто другое
число, это поле в данных расы. Предикаты нужны, когда правило зависит от
обстоятельств броска.

**Не удалять текст `benefit`.** Машинные правила добавляются рядом с ним, а не
вместо. Игрок читает описание, система применяет эффекты, и расхождение между ними
ловится тестом.
