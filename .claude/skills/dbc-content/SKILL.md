# Контент живёт в packs-src, а не в коде

Главное, что ломает старые привычки: **наполнение компендиумов при запуске мира
удалено** (этап 4 плана). Мир их больше не заполняет, файлы `module/constants/*.mjs`
данными компендиумов быть перестали. Править контент правкой библиотеки в коде
теперь бессмысленно — изменение никуда не попадёт.

## Источник истины

| Что | Где |
| --- | --- |
| Библиотеки предметов и акторов | `packs-src/<пак>/` — JSON по файлу на документ |
| Книги | `packs-src/books/<книга>.json` — по файлу на книгу |
| Скомпилированный LevelDB | `packs/` — **не в git**, собирается |
| Список паков | `system.json` → `packs` (сборка берёт список отсюда, не из папки) |
| Раскладка по папкам боковой панели | `system.json` → `packFolders` |

## Две команды

```bash
npm run packs:build
```

```bash
npm run packs:unpack
```

**Порядок безопасный: сначала `packs:unpack`, потом `git diff`, потом всё остальное.**
Сборка стирает папку пака целиком — правки, сделанные руками в Foundry и не снятые
через `packs:unpack`, она потеряет. После клона `packs:build` нужно выполнить один
раз, иначе Foundry увидит пустые компендиумы.

**Круговорот CI (`packs:build → packs:unpack → git diff`) не всегда можно прогнать
локально целиком — есть песочный вариант по ОДНОМУ паку, не рискующий `packs/` или
живым миром (wdbc-04fh).** Приём: `compilePack` из `packs-src/<пак>` во временный
каталог, `extractPack` обратно во ВТОРОЙ временный каталог с теми же
`transformFolderName`/`transformName`, что у `tools/unpack.mjs`, и сравнение
состава+содержимого с исходником. Отвечает ровно на вопрос CI, не трогая ни
`packs/`, ни LevelDB живого мира. Готовый скрипт — `node tools/roundtrip-check.mjs
<пак> [<пак>…]` (рядом с `pack-one.mjs`/`unpack-one.mjs`).

**Не запускать `packs:unpack` (ни отдельно, ни как часть круговорота) во время
параллельной работы нескольких агентов по `packs-src` — и уж тем более не
идти следом `git checkout --`/`git reset`/`git stash`/`git clean` на
основании его вывода.** `unpack`-круговорот НЕ входит в три обязательных
гейта (`npm test`, `npm run lint`, `npm run packs:build`) — это необязательная
самопроверка, и её цена при параллельной работе слишком высока: 14.09.2026
(wdbc-wket) агент прогнал её «для подстраховки», увидел расхождение в файлах
ДВУХ ДРУГИХ параллельных агентов той же сессии (их только что найденные и
записанные `bookSource`), принял это за «чужой устаревший локальный build» и
откатил командой `git checkout --` — стерев 84 файла уже завершённой,
отчитавшейся работы молча, без ошибки. Если нужно проверить именно
целостность своих файлов после правки — читать их обратно (`node -e
"JSON.parse(...)"` на каждый) или, для одного пака, песочный приём одного
пака выше в этом разделе; не полный `unpack` поверх общего рабочего дерева.

## Что проверяет CI

Круговорот: собрать компендиумы из исходников → извлечь обратно → `git diff
--exit-code -- packs-src`. Расхождение хоть на байт — красный пул-реквест. Это ловит
и потерю содержимого при сборке, и расхождение двух инструментов между собой.

Ещё два сторожа по содержанию (23.09.2026), о которых надо знать, правя оружие и книги:

- **Урон оружия сверяется с книгой** — `test/data/damage-notation-vs-book.test.mjs`
  (разбор книжных таблиц — `test/support/book-weapon-rows.mjs`). Тип и подвид урона
  основного профиля И каждого режима (`system.profiles`) должны совпадать с книжной
  нотацией «2d10+2 X(Fr)», и ни один книжный режим не должен теряться. Правишь урон,
  тип, подвид или режимы — прогони этот тест; красный = сверь с книгой (а при
  сомнении в самой книге — с первоисточником в `sources/`), не «чини» тест.
  Исключения там именованные и с причиной: `DEFERRED_TO_SOURCE_PASS` (пак точнее
  книги, решение отложено владельцем) и `NAME_COLLISIONS` (совпали имя и бросок у
  разных вещей).
- **У глав и разделов книг замороженные `_id`** — `test/tools/book-frozen-ids.test.mjs`.
  Добавил раздел в `packs-src/books/<slug>.json` — `node tools/book-stamp-ids.mjs <slug>`;
  существующие `_id` не трогать и не переставлять (иначе ссылки миров на страницы
  книг сиротеют, wdbc-bjy1.10).

## Правила, которые легко нарушить по незнанию

- **`_id` — РОВНО 16 символов `[A-Za-z0-9]`.** Не «до 16». Придуманный руками
  говорящий id (`LocusHeraldFld1`, `DreadTalentsFld` — по 15) проходит ВСЕ гейты:
  `npm test`, `npm run lint`, `npm run packs:build` зелёные. Ломается только живой
  мир, и насмерть: `DataModelValidationFailure … is not a valid 16-character
  alphanumeric ID`, клиент виснет с пустой страницей и `game.ready === false`, а в
  логах сервера при этом «Launching World | Complete» — оттуда не видно. Берите
  случайную строку ровно 16 символов и помните, что id живёт в четырёх местах: `_id`,
  `_key` (`!items!<id>`, `!folders!<id>`), имя файла и поле `folder` у детей
  папки.
- **Ссылки `@UUID` в исходнике книг не хранятся** — сборка расставляет их сама по
  названиям предметов. Сохранённая ссылка попала бы внутрь новой при следующей сборке.
- **Имена файлов в `packs-src/` обрезаны намеренно** (`tools/unpack.mjs`, `NAME_LIMIT`):
  у каталогов снят суффикс-id, название обрезано до 40 символов — иначе кириллические
  пути пробивают потолок Windows в 260 байт и `git checkout` падает с «Filename too
  long». Полное название лежит внутри JSON. Не «чинить» короткие имена.
- **Новый пак** добавляется в `system.json` дважды: в `packs` (иначе не соберётся —
  список берётся из манифеста) и в нужную подпапку `packFolders` по книге-источнику.
  Верхняя папка — «Doom Crusade», организована по книгам-источникам; плоскую общую
  папку не заводить.
- **Поле «книга-источник» — `system.bookSource`, а не `system.source`.** У Черт
  `source` означает механическое происхождение, у Происхождений — «выдано системой
  Происхождений». Разные смыслы, похожие имена.
- **Перед массовым заполнением `bookSource` у нового типа предмета — сверить,
  что поле вообще объявлено в схеме (`module/data/item/<тип>.mjs`) и есть строка
  ввода в его `.hbs`** (`test/data/item-schemas.test.mjs` + `test/templates/
  book-source-row.test.mjs`, разбор — в скилле `dbc-datamodel`). Заполнить JSON
  контентом раньше починки схемы технически можно (JSON примет любое поле), но
  до починки данные недостижимы игроку — молча теряются на сохранении/не видны
  на листе. Правка схемы/шаблона — не твоя зона как контент-агента (`module/`,
  `templates/`), заводи для неё отдельный тикет или проверь, не идёт ли она уже
  параллельно, вместо того чтобы просто дописать данные и остановиться.
- **Доступность = Редкость = «RX» — одна и та же сущность под тремя именами.**
  Поле в схеме — `system.availability` (подписано в листе «Доступность»), в тексте
  книг и в разговоре игроков то же самое зовут «Редкость» или сокращённо «RX», где
  X — уровень. Хранится как знаковый модификатор (`AVAILABILITY`,
  `module/constants/items.mjs`: −5 «Повсеместно» … 0 «Дефицит» … +5 «Уникально»), не
  прямым числом RX — при переносе значения из книги/просьбы игрока сверяться с этой
  таблицей, не считать «R8» напрямую равным `availability: 8`.
- **При расхождении текста между паком и кодом прав пак** — его видят игроки, и после
  этапа 4 он и есть источник истины.

## Честность цитирования книг

Ссылка на книгу проверяется по `packs-src/books/*.json` (дерево `entries[].pages[]`,
у страницы есть `pdfPage` и `html`) — грепом по точной внутрикнижной терминологии, а
не доверием к комментарию в шапке файла. Если содержимое не находится ни в одной
книге, пишем «Домашнее правило (не из официальной книги)», а не выдумываем
правдоподобное название.

**Заполненный `bookSource` может быть хуже пустого — правдоподобная, но
ФИКТИВНАЯ цитата (wdbc-kf5k).** У 8 предметов ship-components стояла точная на
вид ссылка («DoomBC — Книга Пустоты, Линкоры, стр. 182-198») — правильный
раздел, реальный диапазон страниц, полностью транскрибированный
(`checked:true`) — но раздел на этих страницах перечислял ДРУГОЙ, полный
список хуллов без единого совпадения по имени. Пустой `bookSource` хотя бы
честно говорит «не сверено»; такая цитата выглядит проверенной и вводит в
заблуждение того, кто ей поверит не глядя. Аудит непустых `bookSource` (не
только пустых) обязан сверять заявленный диапазон страниц с РЕАЛЬНЫМ
содержимым книги на этих страницах, не только с фактом «поле заполнено».

**Диапазоны книги буквальны: «9» и «8-9» — это грани 9 и 8-9, а НЕ «9 и выше»
(wdbc-l8pj).** Там, где книга имеет в виду «и выше», она пишет диапазон до
предела прямо («7-10», «X+»). Клин Распыления был реализован сравнением `>=` и
заклинивал огнемёт на десятке — тесты повторили ту же ошибку чтения, потому что
писались тем же прочтением книги. Прежде чем писать сравнение по грани кубика —
сверяться, как ТА ЖЕ книга формулирует соседние свойства с диапазоном.

**Пересказ книжного правила в задаче одной сжатой фразой может незаметно
слить ДВА РАЗНЫХ действия книги в одно (wdbc-q2hv).** «Dmg 1d5+S.b при
замахе... дальность при BS+0» смешало Дубину (стр.27) и Метание (стр.28) в один
приём с фиктивным выбором характеристики — реализация по такому пересказу
оказалась структурно неверной, и вскрылось это только когда пользователь прислал
точный текст оригинала уже ПОСЛЕ открытия PR. Формулировку тикета со ссылкой на
страницы книги, если она смешивает разные способы резолва в одну фразу, —
сверять с оригиналом ДО реализации, не только по факту жалобы.

## Аудит зашитых сравнений имени перед переносом на itemHasName

**Substring-regex и exact-match ломаются по-разному — проверять раздельно, не
считать перенос безопасным по умолчанию (wdbc-j9ip).** При аудите «зашитое
сравнение имени предмета → `itemHasName`» полезно различать: `/Слово/i.test(name)`
(substring) почти всегда уже работает на реальных именах пака (подстрока
находится где угодно), а `Set.has(exact)`/`name.startsWith(...)` (anchored/exact)
часто уже сломан молча, потому что реальное имя вида «English / Дар: Русское» не
совпадает с ожидаемым форматом целиком. Прогонять существующий кусок против
реальных имён из `packs-src/` ДО переноса на `itemHasName`, не полагаясь на то,
что перенос ничего не сломает.

## Ловушка: id папки как ДАННЫЕ, не только структура

`kind:"equipment"`+`equipMode:"choice"` (Конструктор, «выбор оружия/брони по
фильтру») хранит `equipWeaponType` — это `_id` РЕАЛЬНОЙ папки компендиума
`weapons`, а не просто путь для UI. У девяти-одиннадцати архетипов Астартес/
Людей этот id указывал на «Азуриане → Рукопашное → Цепное/Силовое» вместо
«Имперское → Рукопашное → Цепное/Силовое» — Обозреватель показывал ТОЛЬКО
эльдарское цепное оружие человеческому/астартовскому архетипу (баг-репорт
20.08.2026, wdbc-2ot). Похоже на автоматический перегон текста в Механику,
искавший папку по ИМЕНИ («Цепное») без учёта ветки фракции и взявший первое
совпадение в алфавитном порядке («Аз…» раньше «Ас…»). `coreWeaponTypeFolders()`
(`module/apps/compendium-browser.mjs`) сама ограничена ТОЛЬКО веткой
«Имперское» — если хранимый id указывает мимо нёе, `describeMechEntry` не
находит имя для подсказки («Снаряжение: выбор — «Оружие» ()» — пустые скобки)
одновременно с неверной фильтрацией: оба симптома лечатся одной правкой
данных. Проверять так: найти `_Folder.json` нужной папки в `packs-src/weapons/
<Ветка>/.../_Folder.json`, сверить `_id` со значением `equipWeaponType` записи.

## Заготовка возможности (`kind:"capability"` без script) — копировать целиком, не печатать руками

Запись `flags.warhammer-dbc.mechanics[].entries[]` с `kind:"capability"` —
плоская схема из ~90 полей (все ветки Конструктора разом: skillScope,
equipMode, weaponPropAction и т.п.), из которых записи с `capabilityKey`
реально используют одно-два. Ручной набор JSON с нуля (16.09.2026, wdbc-1rno.27/
.37, Vigilance/Hair Trigger/Scanning Advance — три Таланта разом) означает
перепечатать все ~90 полей по памяти/наугад — риск опечатки в имени поля или
пропуска дефолта, который молча ломает Конструктор на этом предмете, а не
даёт ошибку сборки (`npm run packs:build` схему не валидирует, только
собирает JSON как есть).

**Не печатать этот объект руками.** Взять `flags.warhammer-dbc.mechanics[0]`
ЦЕЛИКОМ из уже существующего простого примера — `packs-src/talents/Стрелок/
Vigilance___Бдительность_MOP5Z9lsPMk7MFuB.json` (один `kind:"capability"`-
entry, без script-довеска — самый чистый минимальный образец на 16.09.2026),
поменять только `id` группы/entry (на любую другую уникальную строку — в
отличие от `_id` документа выше, ограничение РОВНО 16 символов на ЭТИ id не
распространяется, Foundry не видит их как документы) и `capabilityKey`. Если
нужен ещё и script-триггер (кнопка на предмете) — второй entry в том же
`entries[]` брать из `packs-src/talents/Разбойник/
Blindside___Из_Слепой_Зоны_omwoz55v3z30Fj76.json` тем же приёмом.
