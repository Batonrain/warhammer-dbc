# Правило в данные, а не в код

Цель всего архитектурного плана: игровое отличие описывается записью в данных, а не
`if` в листе персонажа. Прежде чем добавлять ветвление в `module/sheets/` или
`module/combat/`, проверить, не выражается ли оно правилом.

## Сначала прочитать

1. `docs/rules-format.md` — справочник формата: таблица условий `when`, таблица видов
   эффектов, области `target`, `valueFrom`, возможности, вытеснение. **Это источник
   истины, а не текст ниже.**
2. `docs/how-to-add-race.md` — тот же путь целиком, разобранный на сквозном примере
   для человека без опыта в программировании.
3. `docs/architecture-plan.md`, этапы 1–3 — зачем всё устроено именно так.

## Форма записи

```js
{
  id:        "aeldari.eldarten",     // обязателен, уникален, нижний регистр, точка = уровень
  label:     "Eldarten / Эльдарское Тело",
  when:      { race: ["azuriane"], sizeMax: 1 },   // пусто = всегда
  effects:   [{ kind: "rollBonus", target: "initiative", value: 4 }],
  overrides: ["id_другого_правила"]                 // необязательно
}
```

`id` после релиза не меняется — по нему работает вытеснение, это как имя поля в базе.

## Где что лежит

| Файл | Что в нём |
| --- | --- |
| `module/rules/predicates.mjs` | условия `when` — чистые функции `(actor, ctx, value) => boolean` |
| `module/rules/effects.mjs` | перечень известных `kind` и обязательных полей |
| `module/rules/sources.mjs` | откуда правила приходят актору (`race`, `homeworld`, `core`, …) |
| `module/rules/collect.mjs` | `matchRule`, `gatherRules`, `selectRules`, `collectRules` |
| `module/rules/resolve-test.mjs` | конвейер теста, 7 фаз; правила вмешиваются только на 2 и 3 |
| `module/rules/flags.mjs` | `hasRuleFlag(actor, "healing.astartes")` — возможности |
| `module/rules/library/{core,astartes,aeldari}.mjs` | сами правила по книгам |

## Порядок работы

1. **Разобрать правило книги на две части.** Текст `benefit` остаётся описанием для
   игрока и **не удаляется никогда**. Машинная часть пишется рядом.
2. **Перевести в данные только то, что система считает.** Иммунитет к людским
   болезням и долгожительство применяет мастер — им место в тексте, а не в `effects`.
3. **Положить правило в `library/<книга>.mjs`** и привязать к источнику (например,
   поле `rules` у расы в `module/constants/races.mjs`).
4. **Не дублировать отбор.** Если правило приходит от источника `race`, условие
   `when: { race: [...] }` лишнее — источник уже выбрал. Вторая проверка разойдётся с
   источником при первой же правке.
5. **Написать три теста:** подходит, не подходит по основному условию, не подходит по
   расе. На литерале-акторе, без Foundry.
6. `npm test` и `npm run lint`.

## Нового предиката может не понадобиться

Если у расы просто другое число — это поле в данных расы, а не предикат. Предикаты
нужны, когда правило зависит от обстоятельств броска.

Если предикат всё же нужен, требования к нему не обсуждаются: чистая функция (никаких
`game`/`ui`/`canvas`/бросков), безопасен к отсутствию полей (`?.` и `?? 0` везде),
возвращает строго `true`/`false`. Неизвестный ключ условия жалуется в консоль и даёт
`false` — опечатка в данных не должна проходить молча.

## Возможность вместо проверки расы

`system.race === "astartes"` в игровой логике — сигнал завести возможность:

```js
{ kind: "grantFlag", target: "healing.astartes" }   // в правиле
hasRuleFlag(patient, "healing.astartes")            // в коде
```

Имя возможности — название правила книги, а не расы, даже когда раса в нём упомянута.
Новое имя заводится **вместе** с местом, которое его читает: флаг без читателя молча
ничего не делает. Проверки, управляющие только показом блока в интерфейсе, остаются
как есть — это не игровая логика.

## Вытеснение

`overrides: ["smite.baseline"]` — ответ на «у Астартес своя версия». Порядок в
`collectRules` обязателен: собрать всё → отобрать по `when` → **и только потом** снять
вытесненные. Правило с невыполненным условием не должно ничего вытеснять. Взаимное
вытеснение двух прошедших отбор правил — ошибка в данных: пишем в консоль и оставляем
оба, потому что молча выбранное одно хуже двойного эффекта, который сразу заметят.

## Чего не делать

- **Не решать вариативность через `kind: "script"`.** Свободный JS снимает задачу
  сегодня и возвращает через полгода, только теперь размазанной по сотням предметов,
  вне git и вне тестов. Допустим, когда правило действительно нельзя выразить данными,
  и тогда рядом пишется комментарий с объяснением почему.
- **Не складывать `fearRating`.** Два источника с рейтингом 2 дают 2, а не 4.
- **Не удалять текст `benefit`.**
