# Тип документа на TypeDataModel

Шаг 5.1 плана, **идёт прямо сейчас**. `template.json` на 53 КБ описывает 10 типов
акторов и 35 типов предметов без валидации и без `migrateData`; опечатка в пути поля
проявляется тихим `undefined` в расчётах. Типы переводятся по одному.

Состояние: переведены `weaponProperty`, `aspiration`, `trait`. Осталось 32 типа
предмета и 10 типов актора, `character` — последним.

## Куда что кладётся

| Файл | Роль |
| --- | --- |
| `module/data/item/<тип>.mjs` | класс схемы, `extends foundry.abstract.TypeDataModel` |
| `module/data/index.mjs` | `ITEM_DATA_MODELS` — тип → класс |
| `warhammer-dbc.mjs` (хук `init`) | `Object.assign(CONFIG.Item.dataModels, ITEM_DATA_MODELS)` |
| `template.json` | запись типа **опустошается в том же коммите**: `"trait": {}` |

Сам тип из списка `types` в `template.json` не убирается — им он и объявлен.
Опустошать запись обязательно: зарегистрированный тип её больше не читает, а два
описания одной схемы разъедутся при первой правке.

## Образец

```js
export class AspirationData extends foundry.abstract.TypeDataModel {
  /** @override */
  static defineSchema() {
    const { StringField, NumberField } = foundry.data.fields;
    return {
      table: new StringField({ initial: "pride", choices: ASPIRATION_TABLES, label: "Таблица" }),
      n:     new NumberField({ initial: 0, integer: true, nullable: false, label: "Номер в таблице" })
    };
  }
}
```

Шапка файла объясняет, что это за сущность по книге и почему поля именно такие — так
устроены все файлы проекта, держать стиль.

## Перевод проверяется двумя вопросами

Оба — в `test/data/item-schemas.test.mjs`:

1. **Умолчания.** Новый предмет получает ровно то, что раздавал `template.json`.
2. **Сохранность.** Каждый документ этого типа из `packs-src` проходит через схему
   без потерь. Поле, забытое в `defineSchema()`, Foundry не сохранит — и данные книги
   исчезнут при первой правке предмета в игре.

Вторая проверка не формальность: на первом же типе она нашла поле `requirement` у
Черт, которого в `template.json` не было никогда, но которое читает пикер Черт.

## Миграция

Если у типа в реальных данных встречаются два формата одного и того же — пишем
`static migrateData(source)` и оставляем один. **Проверяется не форма записи, а
равенство результата:** то, что получается из данных до и после миграции, должно
совпадать (образец — `test/data/trait-migration.test.mjs`, где сравниваются `changes`
от `legacyEffectsToChanges`). Данные для теста брать из `packs-src` — настоящие
записи прошлого формата, а не выдуманные.

Не описывать схемой то, что снимается. У Черты поле `effects` объявлено свободным
объектом: механика переезжает в `ActiveEffect`, и перечисление её ключей закрепило бы
формат, от которого уходим.

## Заглушка Foundry в тестах

`test/support/foundry-stub.mjs` умеет `StringField`, `NumberField`, `BooleanField`,
`ObjectField` и `TypeDataModel` с тем же порядком инициализации (`migrateData`, потом
очистка полей). **Валидацию заглушка не изображает** — недопустимое значение поля с
`choices` она пропустит, а настоящий Foundry поднимет ошибку. Поэтому тесты
спрашивают про умолчания и сохранность, а не про поведение на заведомо неверных
значениях: иначе проверялась бы заглушка, а не схема.

Если для теста понадобился новый тип поля — дописать его в заглушку, а не тащить в
тест настоящий Foundry.

## Готово, когда

Тип переведён, запись в `template.json` опустошена в том же коммите, старые миры
открываются, `migrateData` (если он есть) покрыт тестом на данных прошлого формата.
`npm test` и `npm run lint` чистые. Открытие мира со старыми предметами смотрится
руками в Foundry — как войти, описано в `.claude/skills/dbc-workflow/SKILL.md`.
