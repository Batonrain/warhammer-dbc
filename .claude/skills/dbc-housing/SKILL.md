# Housing в реальном коде

Все 10 текущих листов актора перенесены и проверены вживую (журнал и номера
задач — в трекере `bd`, здесь не дублируются). Ниже — рабочий рецепт, не
гипотеза: для нового типа актора или сверки при правке готового листа.

**Два готовых архетипа переноса, определи сразу какой:**
- **«Тонкая обёртка над Персонажем»** (Миньон) — лист `extends
  WarhammerCharacterSheet`, реюзает те же партиалы вкладок (уже когитаторные
  сами по себе). Меняешь только свою шапку/nav/root — обшивка вкладок
  приходит бесплатно. `actor.type` листа НЕ `"character"` → его нужно
  добавить в allow-list `_applyThemeClasses()` (`actor-sheet.mjs`) рядом с
  `"character"`, иначе `cog-frame` не навесится (Демон/Демон-Принц в этом же
  allow-list'е остаются исключены — allow-list растёт, не превращается в
  общий класс).
- **«Полностью самостоятельный лист»** (Отряд, Орда) — свой `extends
  ActorSheetV2`, своя тема, свои классы `.sq-*`/`.horde-*`. Если тема НЕ
  когитаторная и тикет прямо говорит «не перекрашивать» (см. п.3) — вкладки
  НЕ переделываются под стиль Проводника, housing просто оборачивает то, что
  есть, как есть. Сверить с мокапом: если артборды сохранили родные
  `.<sheet>-tabs .item.active` дословно — значит редизайна нет, только
  обшивка.

## 0. Прочитать сначала

1. `bd show <тикет>` — Acceptance Criteria обычно уже фиксируют, какие вкладки
   какой темы (когитатор/пергамент/своя палитра) и что явно ОТЛОЖЕНО (другие
   типы акторов, перенос отдельных полей и т.п.) — не решать это самому.
2. Мокап, на который ссылается тикет — тот же артефакт Design Canvas
   (`https://claude.ai/code/artifact/83ecd8cc-5079-466e-9874-4bc5af99d648`,
   если тикет не называет другой). Прочитать его `<helmet><style>`-блок
   ОДНОГО артборда через `Artifact action:"read"` (для собственного артефакта
   возвращает сырой HTML, путь к сохранённому файлу — в результате вызова) —
   не пытаться угадать точные значения по описанию тикета.
3. Реальные `.hbs`/`.css` листа, который дорабатываешь — сверить, что мокап
   строился по актуальному состоянию (мокап мог устареть, см. `doombc-mockup`
   про определение темы вкладки).

## 1. ApplicationV2-грабли — прочитать ПЕРЕД правкой .hbs

**`PARTS.<part>.root = true` отбрасывает класс/inline-style, написанные прямо
на корневом `<div>` шаблона — доходят только его ДЕТИ.** Проверить у листа:
`static PARTS = { body: { template: "...", root: true } }` — если стоит (а у
всех листов актора в этом проекте стоит), любой новый класс на самом корне
(`cog-frame` и т.п.) нужно навешивать в JS (метод, вызываемый на каждом
рендере — `_applyThemeClasses()`/аналог в `_onRender`), НЕ писать в шаблоне.
Housing-ЭЛЕМЕНТЫ (`.cog-rivet`, `.cog-plate-row`, `.cog-screen`, `.cog-status-
row`) — это дети корня, они спокойно пишутся прямо в `.hbs` и доходят до DOM
без проблем; страдает только класс/style на САМОМ корневом теге.

**Если у листа НЕТ единого корневого `<div>` в шаблоне** (несколько соседних
тегов на верхнем уровне — `<header>`, `<nav>`, `<div class="sheet-body">`, как
у `squad-sheet.hbs`) — `root:true` в этом случае просто переносит ВСЕ
top-level элементы шаблона детьми в `this.element`, который уже несёт нужные
классы из `DEFAULT_OPTIONS.classes` (см. ниже). Тогда обёртка `.cog-frame` не
нужна вовсе — housing-элементы (рivets/plate-row/screen/status-row) пишутся
как top-level соседи прямо в шаблоне, а CSS сразу скоупится на существующий
класс листа (`.warhammer-dbc.squad-sheet` и т.п.), если он не унаследован
(следующий пункт).

**`DEFAULT_OPTIONS.classes` СКЛЕИВАЕТСЯ по всей цепочке наследования, а не
берётся только у своего класса.** Если лист `extends` другой лист листа
(`WarhammerDaemonSheet extends WarhammerCharacterSheet`), он получает классы
ОБОИХ — `grep "extends Warhammer.*Sheet"` по `module/sheets/` перед тем, как
скоупить новый CSS на класс базового листа: этот класс не эксклюзивен для
базового листа, если у него есть подклассы. Практика:
- Если у листа есть подклассы (character-sheet → daemon/demon-prince) —
  класс базового листа НЕ безопасный маркер. Добавить своё новое имя класса
  (`cog-frame`) через JS в per-render хуке, гейтя по РЕАЛЬНЫМ данным
  (`this.actor.type === "character"`), не по названию класса.
- Если подклассов нет (проверено `grep`, как у `WarhammerSquadSheet`) —
  существующий класс листа (`squad-sheet`) уже безопасен, отдельный
  JS-маркер не нужен.

Оба пункта и живая проверка (Демон НЕ получил обшивку персонажа) — в памяти
`doombc-foundry-v13-gotchas` (личная память сессии, не в репозитории).

**Если лист claims тему через CSS custom properties/класс, написанные
инлайном на корне `.hbs` (`--gc`/`--dp-hue` и т.п.) — ПРОВЕРИТЬ вживую ДО
того, как полагаться на существующую реализацию.** На Демоне и Демон-Принце
(wdbc-nzn7/wdbc-xzvt) обнаружилось: `--gc`/`--gc2`/`--glow`/`--dp-hue`,
написанные на том самом отбрасываемом корневом `<div>`, НИКОГДА не
применялись к живому DOM — оба листа с момента написания красились в дефолт
«Неделимый» независимо от выбранного Бога, у Демон-Принца вдобавок была
мертва вся резервная палитра (`--wh-bg`/`--cg`/`--wh-text`), потому что
`DEFAULT_OPTIONS.classes` нёс `"demon-prince"`, а не буквальную строку
`"demon-prince-sheet"`, на которую скоупились все правила темы. Ни один тест
это не ловил, а на глаз по коду и по сверке с мокапом всё выглядело
правильно. **Проверка:** `getComputedStyle(sheet.element).getPropertyValue
('--var')` не должно быть `""`, плюс `grep` буквальной строки CSS-класса из
`.hbs` в `DEFAULT_OPTIONS.classes` того же `.mjs`. Если баг подтвердился —
фикс тот же паттерн, что `_applyChaosPatronTheme()`: свой метод
(`_applyDaemonTheme()`/`_applyDpTheme()`), вызываемый из `_onRender`, ставит
переменные/класс на `this.element`; недостающая строка класса добавляется в
`DEFAULT_OPTIONS.classes` отдельным пунктом (полная запись — в
`doombc-foundry-v13-gotchas`).

**Фон `.cog-frame`/корня листа нужен с `!important`.** Установленный модуль
Monk's Little Details красит фон ЛЮБОГО `.application` своим правилом
`body.change-windows.theme-dark:not(...) .application:not(.theme-light):
not(.image-popout):not(.prosemirror)` — специфичность (0,7,1), выше любого
разумного нашего селектора. Без `!important` на `background` рамка визуально
плоско-серая вместо металла, а padding/border/box-shadow при этом выглядят
нормально (те свойства модуль не трогает) — компьютед-стайл по одному
свойству легко пропустить эту дыру. Поймано только через обход
`document.styleSheets` с рекурсией по `CSSImportRule.styleSheet` (обычный
перебор `document.styleSheets` без рекурсии ничего не находит — все правила
системы сидят внутри `@import`). Обнаружено 29.08.2026 задним числом — у
УЖЕ ЗАКРЫТОГО wdbc-m6as (Персонаж) был тот же баг, никто не заметил на
скриншоте. Проверять явно: `getComputedStyle(el).backgroundImage` должно
начинаться с `"repeating-linear-gradient"`, а не быть `"none"`.

## 2. Общий DOM/CSS-каркас (одинаковый для любого листа)

**НИКОГДА не ставить `position: relative` (или любой `position` кроме
`fixed`) на корневое правило, которое матчит сам `this.element` листа**
(в этом рецепте — комбинированный селектор вида `.character-sheet.cog-frame,
.squad-sheet` в actor-housing.css). `this.element` — РЕАЛЬНОЕ плавающее окно
Foundry, которому `.application` уже даёт `position: fixed`; переопределение
на `relative` вынимает окно из fixed-позиционирования, оно становится
обычным flex-ребёнком `<body>` (body у Foundry — `display:flex`) и начинает
отжимать по ширине `#interface` (тоже flex-ребёнок body) — с виду вообще не
похоже на баг housing: жалоба выглядит как «открытие листа странно сдвигает
боковую панель» (`#sidebar` внутри `#interface` в итоге уезжает за экран).
Проверено и исправлено 29.08.2026 — баг сидел молча в ОБОИХ уже закрытых
тикетах (wdbc-m6as, wdbc-0owk) от самого их первого прохода, пока не всплыл
на живой кампании. `.cog-rivet` (position:absolute) не нуждается в
`position:relative` на предке специально под это — `position:fixed` от
`.application` уже валидный containing block. Диагностика: `getComputedStyle
(document.querySelector('.<класс-листа>')).position` должно быть `"fixed"`
(в живом Foundry иногда репортится как `"absolute"` — тоже нормально, лишь
бы НЕ `"relative"`/`"static"`); также сверить, что `#sidebar`
`getBoundingClientRect()` не меняется до/после открытия листа.

```html
<div class="cog-rivet tl"></div>
<div class="cog-rivet tr"></div>
<div class="cog-rivet bl"></div>
<div class="cog-rivet br"></div>

<div class="cog-plate-row">
  <span class="cog-plate">Инфопланшет модели XIL</span>
  <div class="cog-leds">
    <i class="cog-led cog-led-green on"></i>
    <i class="cog-led cog-led-amber {{#if ...}}on{{/if}}"></i>
    <i class="cog-led cog-led-red {{#if ...}}on{{/if}}"></i>
  </div>
</div>

<div class="cog-screen">
  {{! header + nav.sheet-tabs + div.sheet-body — без изменений структуры }}
  <div class="screen-status-line"><i class="cog-status-dot"></i><span>...</span></div>
</div>

<div class="cog-status-row"></div>
```

**Статус-строка (`.screen-status-line`) не обязательна** — если мокап её не
рисует ни на одном артборде листа (как Орда, все 4), не придумывать самому.

**Если у листа корень (`.wh-<sheet>`/`.<sheet>-sheet-form` и т.п.) раньше сам
служил контейнером с собственным `padding`/`gap` для прямого контента**
(header/nav/body были его прямыми детьми) — после того, как `.cog-frame`-
правило переопределит на нём `padding`/`background` под housing, этот старый
отступ/интервал нужно вернуть, но уже на `.cog-screen` (она встаёт МЕЖДУ
корнем и старым контентом, отступ логически принадлежит ей). Точечное
правило в CSS-файле конкретного листа, например:
```css
.warhammer-dbc.wh-horde .cog-screen { padding: 7px; gap: 6px; }
```
Не трогать общий `.cog-screen` в actor-housing.css — падинг/gap там разный
для разных листов (Персонаж/Отряд их не имели вовсе, полагаясь на padding
внутренних `.sheet-header`/`.sheet-body`).

`.cog-screen` — контур-кольцо ОДНИМ элементом (не рамка на каждой панели):
```css
.cog-screen {
  border: 7px solid transparent;
  border-radius: 4px;
  background:
    linear-gradient(var(--wh-bg), var(--wh-bg)) padding-box,
    linear-gradient(150deg, #e2e2e2, #7a7a7a 28%, #242424 52%, #8c8c8c 76%, #dcdcdc) border-box;
  box-shadow: inset 0 0 0 1px rgba(0,0,0,0.65), 0 8px 26px rgba(0,0,0,0.5);
}
```
Двойной `background` (padding-box + border-box) — единственный способ дать
скошенный металлический ободок без лишнего слоя разметки. `.cog-frame`/
`.cog-plate-row`/`.cog-led`/`.screen-status-line` — взять целиком из
`styles/sheets/actor-housing.css` (уже реализовано для персонажа), копировать
и подставлять только тему-специфичные значения (см. ниже про пергамент).

**Полный референсный файл — `styles/sheets/actor-housing.css`.** Копировать
оттуда, не писать заново по памяти — оттенки/тени уже подобраны и проверены
вживую.

## 3. Тема панелей — НЕ всегда когитатор

Housing (металл, заклёпки, LED) — ВСЕГДА один и тот же независимо от темы
листа. А вот `.sheet-body`/панели красить в зелёный когитатор нужно, только
если у листа реально есть терминальная тема (см. `doombc-mockup` → «Определение
темы вкладки» — та же проверка применима и здесь: искать `*-cog.css` файл
для ИМЕННО этого листа в `@import`-списке `styles/warhammer-dbc.css`). Если
файла нет — панели остаются на обычном `var(--wh-parchment)`, только housing
вокруг него металлический. У листа Отряда (wdbc-0owk) `squad-cog.css` нет
вовсе — весь лист пергаментный, обшивку красить в зелёный НЕ нужно.

## 4. Вкладки в стиле Проводника

Активная вкладка получает фон `.sheet-body` (обычно один и тот же контейнер
на все вкладки листа — проверить, не различается ли фон реально по вкладкам
у конкретного листа, прежде чем полагаться на это) и `border` без нижней
грани — отсюда «перетекание» без шва. Неактивная полоса — заметно темнее.

**Акцентный цвет отдельных вкладок со своей палитрой (Мистика/Тех у
персонажа) НЕЛЬЗЯ прокинуть через наследование CSS-переменной** — `--pc`/
`--mc` заданы на div самой вкладки-контента (`.psy-tab`/`.tech-tab`), который
СОСЕД полосы вкладок, а не её предок. Наследование переменных идёт только
вниз по DOM, вбок — нет. Рабочий приём: захардкодить известное статическое
значение акцента прямо в правиле полосы вкладок:
```css
.sheet-tabs .item[data-tab="psy"].active { border-color: #b477ff; animation: cogTabGlowPsy 4.5s ease-in-out infinite; }
@keyframes cogTabGlowPsy { 0%,100% { text-shadow: 0 0 6px #b477ff; } 50% { text-shadow: 0 0 13px #b477ff; } }
```
Не пытаться зарефакторить существующую цепочку общих `--cg`-селекторов под
это — она общая для десятка других правил, трогать рискованно; отдельное
точечное правило с более высокой специфичностью (доп. атрибутный селектор)
безопаснее и уже проверено (не ломает уже существующую подсветку патрона
Хаоса `chaos-heretic.css`, которая переопределяет тот же `box-shadow` с той
же специфичностью, но грузится позже — работает как раньше).

## 5. Ассеты — CSS-спрайт, не офлайн-нарезка

Источник текстуры — `Dataslate 2.png` (1131×1600), реально лежит в мире
`worlds/iz-pepla/assets/art/overlays/`, НЕ в системе. Скопирован разово в
`systems/warhammer-dbc/assets/overlays/dataslate.png` — переиспользовать этот
файл, не копировать заново из мира.

Не резать на отдельные PNG офлайн (хрупко, лишний шаг с PIL/альфа-маской) —
один `background-image` + `background-position`/`background-size` на разные
маленькие элементы. Уже подобранные крои (пиксели ИСТОЧНИКА 1131×1600):
- Заклёпка tl: `(30,30)–(190,190)` · tr: `(941,30)–(1101,190)` · bl:
  `(30,1410)–(190,1570)` · br: `(941,1410)–(1101,1570)` — квадрат 160×160
  вокруг черепа в каждом углу.
- Решётка (центр нижней полосы, без боковых черепов): `(190,1420)–(941,1600)`
  — 751×180.

Формула: `scale = целевой_размер / размер_кроя`; `background-size =
1131*scale × 1600*scale`; `background-position = -crop_x*scale, -crop_y*scale`.
Пример (заклёпка 34px из кроя 160px, scale=0.2125): `background-size: 240px
340px`, tl → `background-position: -6px -6px`.

## 6. LED — не выдумывать своё состояние

Зелёный — всегда `on`. Жёлтый/красный тикет обычно оставляет открытым
(«по состоянию», без деталей) — не изобретать новую переменную, привязать к
уже посчитанному производному полю актора этого типа (у персонажа —
`system.wounds.tier`: healthy/light/heavy/dying → amber на heavy, red на
dying; у Отряда — `derived.cohesionBand`: amber на "strained", red на
"spent", тот же принцип «два худших деривед-состояния» без новой логики).
Если у листа (Техника и т.п.) нет очевидного аналога «здоровья» — спросить
пользователя одним чётким вопросом с рекомендованным вариантом, не решать
молча, ПОКА для этой категории листа нет уже подтверждённого пользователем
прецедента; если прецедент есть (как выше) — можно применить ту же логику
по аналогии без повторного вопроса, но явно отметить выбор в итоговом
докладе, чтобы пользователь мог поправить. Ещё пары: Формирование —
`derived.routed` (amber) / `derived.broken` (red); Корабль — `derived.hi.
crippled`/демонический статус.

**Если у листа НЕТ ВООБЩЕ никакого аналога «состояния/опасности»** (Звёздная
система, wdbc-70g5 — пассивный лист состояния мира, не боевой актор) — не
пытаться натянуть что-то отдалённо похожее (список неразведанных тел, факт
аномалии и т.п.). Оставить amber/red LED статично выключенными (только
зелёный «питание есть»), явно отметить это как сознательный выбор в докладе.

## 7. Проверка

- **Если тикет просит убрать вкладку из навигации — искать её ТАКЖЕ в
  `static TABS` конкретного `*-sheet.mjs`, не только в `.hbs`.** Список
  вкладок дублирован в двух местах (класс листа знает список для
  ApplicationV2, шаблон рисует `<nav>`); убрать только из `.hbs` — контракт-
  тест (`test/sheets/*-v2.test.mjs`, «вкладки класса и разметки совпадают»)
  тут же ловит рассинхрон, но дешевле сразу проверить оба места (`grep
  '"<id-вкладки>"' module/sheets/<sheet>.mjs`). Наступил на это при слиянии
  вкладки «Ангар» у Корабля (wdbc-zuf4).
- **Когда тикет просит «список категорий сверить с реальными правилами» и
  прямо признаётся, что источника истины не было на момент мокапа** — не
  гадать заново, а поискать уже существующую в коде labeled-константу того
  же домена (`KIND_LABELS`, `SHIP_DISTORTIONS`, что-то в
  `module/constants/*`). У Корабля (wdbc-zuf4) нужный список 4 категорий
  обязательных узлов УЖЕ был явно назван в `KIND_LABELS`
  (`module/sheets/ship-sheet.mjs`) — не пришлось выдумывать свою
  классификацию.
- **В живом мире может не быть НИ ОДНОГО актора нужного типа** (так было с
  Миньоном и Ордой — ни одного во всей `iz-pepla`, хотя мокап их
  показывает). Не отказываться от живой проверки — создать одноразовый
  `Actor.create({name:"ТЕСТ_housing_<тип>_не_трогать", type:"<тип>"})`
  прямо в `javascript_tool`, проверить, `await actor.delete()` в конце
  безусловно (тот же протокол, что у `sheet-inspector`).
- `npm test` — обязательный гейт (см. `dbc-workflow`). `npm run packs:build`
  — только если тикет реально трогал `packs-src/`; если нет, гейт
  неприменим — сборка на общем репо часто откажет сама («В компендиумах
  есть правки, которых нет в исходниках») из-за чужих параллельных сессий,
  и `--force`/`packs:unpack` здесь ЗАПРЕЩЕНЫ — снесут чужую незакоммиченную
  работу (см. `doombc-unpack-stale-compiled-pack-danger`, личная память).
- Проверить фон корпуса явно, а не полагаться на «выглядит похоже»:
  `getComputedStyle(document.querySelector('.<класс-листа>')).backgroundImage`
  должно начинаться с `"repeating-linear-gradient"` — см. п.1 про Monk's
  Little Details, обычный computed-style по border/padding эту дыру не
  ловит.
- **Обязательно проверить `position` корня и то, что боковая панель Foundry
  не двигается** (см. предупреждение в п.2 про `position:relative`) —
  `getComputedStyle(document.querySelector('.<класс-листа>')).position`
  (НЕ `relative`/`static`) и `#sidebar`'s `getBoundingClientRect()` до/после
  открытия листа должны совпасть. Этот баг не виден на обычном скриншоте
  самого листа — нужно смотреть на весь экран целиком.
- Живьём в Foundry — взять лок `wdbc-a4l` (`bd update wdbc-a4l --claim`,
  освободить `--status open --assignee ""` по готовности, см.
  `dbc-workflow`).
- **Скриншот в этом окружении часто ненадёжен для мелких деталей** —
  `zoom`/кроп области у `computer` в Browser pane не поддержан («region crop
  not yet supported»), плюс сам Foundry иногда не композится в панели.
  Надёжнее опрашивать реальный DOM через `javascript_tool`:
  `getComputedStyle(el)` на `.cog-rivet`/`.sheet-tabs .item.active` и
  сверять `backgroundPosition`/`backgroundSize`/`borderColor` с посчитанными
  числами, а не полагаться на то, что «на скриншоте вроде похоже». Для
  LED/тир-зависимых состояний — временно `actor.update(...)`, проверить,
  ОБЯЗАТЕЛЬНО откатить тем же вызовом сразу после (никогда не оставлять живой
  тестовый актор изменённым).
- **Обязательно проверить, что обшивка НЕ протекла на другой тип листа**,
  если у правленого листа есть подклассы (см. п.1): открыть лист подкласса
  (`document.querySelectorAll('.character-sheet')` → сравнить `className`
  разных открытых листов, или конкретно искать класс-маркер housing) и
  убедиться, что маркер туда не попал.

## Область применения задачи

Каждый тикет переноса housing обычно ограничен ОДНИМ типом листа (см. wdbc-
m6as — только персонаж, другие типы явно отложены). Не расширять на другие
листы по своей инициативе — заводить/предлагать отдельный тикет.
