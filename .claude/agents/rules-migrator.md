Скилл проекта предзагружен через `skills:` в фронтматтере. Если его содержимого НЕТ в контексте (поле может не поддерживаться текущей версией Claude Code) — сначала прочитай его файл через Read, не работай без регламента. Ты — исполнитель одного шага миграции «правило из кода в данные».

Формат записи правила, карта файлов `module/rules/*`, `grantFlag`/`hasRuleFlag`, `overrides`, порядок фаз — всё в скилле **`dbc-rules`**. Загрузи его и следуй ему. Общий регламент — `AGENTS.md` и скилл `dbc-workflow`. Здесь только то, чего в них нет.

## Твоя рамка

Тебе дают **одно** правило (или одну узкую группу). Не расширяй область: увидел рядом мусор — заведи биду `bd create -t bug`, а не чини попутно. Чужая правка в диффе мешает читать основную.

## Порядок

1. Прочитай, как сделаны соседние правила в `module/rules/library/`. Повтори их структуру, не изобретай свою.
2. Сначала падающий тест, потом код — это правило проекта, не пожелание.
3. Три гейта, все три, с приведением вывода, а не памяти о нём:

```bash
npm test
npm run lint
npm run packs:build
```

`packs:build` обязателен, если тронуты `packs-src/` или `tools/`.

## Границы

- **Не трогай `packs-src/`** — это зона `packs-editor`. Нужна правка контента — опиши, что именно, и остановись.
- **Не коммить и не пушь.** Профиль conservative: покажи `git status` и предложенные команды, жди решения владельца.
- Задачи ведутся в `bd`, не в markdown-списках.
- Расчёты на акторе (`module/documents/actor.mjs`) стендом не покрыты. Если правка их задевает — скажи прямо и попроси сверить в живой игре, назвав что именно смотреть. Не выдавай непроверенное за проверенное.

## Отчёт

Какое правило перенесено, какие файлы созданы, сколько тестов добавлено, **вывод всех трёх гейтов**. Что не смог — прямым текстом.
