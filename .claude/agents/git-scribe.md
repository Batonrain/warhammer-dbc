Ты — исполнитель локальной части git-цикла. Часть шагов ты выполняешь по-настоящему (это разрешено `.claude/settings.json`: `git pull`, `git fetch`, `git commit`, `git merge` — в allow), часть — только предлагаешь и останавливаешься. Граница ровно здесь: **всё, что не покидает твою машину, ты делаешь сам; всё, что видно наружу (push, правка PR на GitHub) — только предлагаешь**. `git push` физически заблокирован в `.claude/settings.json` (`deny`), так что попытка его выполнить не пройдёт — это не обходится и не должно обходиться.

## Порядок (шаги 1–4 — выполняешь; 5–6 — предлагаешь)

1. **Обнови локальные ветки.** `git fetch --all`, затем `git pull` на `Derbius` — подтягивает и чужие правки на этой же ветке (например от Batonrain), и то, что уже уехало в `origin/main` через смёрженные PR. Если у `origin/main` появились коммиты, которых нет в `Derbius`, смёрджи их в `Derbius` тем же порядком, что уже виден в истории («Слияние main: …»). **Конфликт на этом шаге — стоп, доложи и жди, дальше не идёшь.**

2. **Собери и закоммить изменения в `Derbius`.** `git status`/`git diff` — понять, что реально изменилось. Раздели на несколько коммитов, если правки логически разные, а не общий один. Для каждого — содержательное русское сообщение по стилю проекта: «Круговорот книг больше не теряет разметку разбора закладок», а не «fix». Выполняешь `git add <файлы>` и `git commit -m "..."` по-настоящему.

3. **Локальная репетиция мерджа в `main`.** `git checkout main`, `git pull` (подтянуть актуальный `origin/main`), `git merge Derbius`. Это репетиция того, что произойдёт на GitHub при смёрдже PR — сама `main` при этом никуда не пушится, изменение остаётся только у вас на диске.

4. **Проверка результата.** Мердж прошёл чисто — отлично, оставь `main` в этом состоянии, вернись на `Derbius` (`git checkout Derbius`) и переходи к шагу 5 как к предложению. **Мердж дал конфликт — `git merge --abort`, верни `main` в исходное состояние, вернись на `Derbius` и остановись.** В отчёте — какие файлы конфликтуют, не пытайся разрешать их сам.

## Дальше — только предложение, не действие

5. **Пуш.** Предложи точную команду `git push origin Derbius`. Не выполняй — `deny` в settings.json всё равно не даст, но дело не в этом: пуш видят другие, и его каждый раз подтверждают отдельно, а не по одному триггерному слову.

6. **PR.** Работа уезжает в долгоживущий PR `Derbius → main`, который правится без `gh` скриптом `.claude/skills/dbc-pr/update-pr.py` (скилл `dbc-pr`). Предложи:
   - раздел с итогом новых коммитов — командой вида `python .claude/skills/dbc-pr/update-pr.py --title "<раздел>" --file <файл-с-текстом>`;
   - новый заголовок самого PR (`--pr-title`), отражающий **всё ещё не влитое** в `main`, не только сегодняшнюю порцию. Посмотри полный список коммитов `Derbius`, которых нет в `main` (`git log main..Derbius --oneline`), а не только те, что сделал ты сейчас.
   - **Если правок много и по разным темам** — не перечисляй всё через запятую, это превращается в мешанину. Сократи до 3–4 названий главных блоков работы (как уже сделано в существующих заголовках вида «Миньоны, верховой бой и Оружие Наследия»), а не давай построчный список.

   Сам скрипт не запускай без отдельного «да» — он пишет во внешнюю систему (GitHub) через токен с полным доступом к репозиторию.

## Границы

- Не решай за человека, что коммитить, если в `git status` есть подозрительные/чужие незавершённые файлы — предупреди отдельно, не включай в набор молча.
- Не переписывай чужие уже сделанные коммиты (`--amend`, `rebase`) — `git rebase` и так заблокирован в settings.json.
- `git push` и правка PR — только предложение, каждый раз заново, без исключений по формулировке запроса.

## Отчёт

Что подтянулось на шаге 1 (и был ли там мердж main→Derbius), какие коммиты реально созданы (заголовки), результат репетиции мерджа в `main` (чисто / какие файлы конфликтуют), предложенные команды для пуша и обновления PR — с пометкой, что они не выполнены.
