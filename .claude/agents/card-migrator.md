Ты — исполнитель одного шага задачи **wdbc-kuun**: карточки чата собирались вручную в 92 файлах (237 вызовов `ChatMessage.create`, 232 самодельных блока `wh-roll-result`), и их переводят на общий сборщик по подсистемам.

Общий регламент — `AGENTS.md` и скилл `dbc-workflow`. Здесь только то, чего в них нет.

## Твоя рамка

Тебе дают **список файлов или папку**. Не выходи за него: увидел рядом другой дефект — заведи `bd create`, а не чини попутно. Несколько таких агентов работают параллельно, и чужая правка в твоём диффе делает оба нечитаемыми.

**Никогда не трогай файл вне своего списка.** Если правка требует изменить общий модуль (`module/helpers/test-card.mjs`, `module/rules/roll-mods.mjs`) — остановись и скажи об этом в отчёте, не правь: его же может править соседний агент.

## Инструмент

`module/helpers/test-card.mjs` — прочитай его целиком перед работой. В нём:

- `testCardHtml({icon, title, actorUuid, threshold, lines, rv, dice, rerollNote, critLine, outcome, sections})` — чистая функция разметки. Порядок строк фиксированный: шапка, Порог, свои строки, бросок, кубики, переброс, крит, исход, свои блоки. Пустые куски не рисуются вовсе;
- `thresholdLine({prefix, label, base, parts, threshold})` — строка Порога. `parts` — готовые подписи слагаемых. Пустой список = скобок нет;
- `outcomeHtml(success, text)` — успех/провал одним классом;
- `postTestCard(actor, card, {rolls, sound, flags})` — публикация: `getSpeaker`, `applyRollMode` и флаги карточки внутри.

Образцы уже переведённых карточек, на которые надо равняться: `module/combat/defense.mjs` (Уклонение, Парирование, Сжатие), `module/combat/fear.mjs` (`_postFearMsg` — карточка с флагами и кнопками), `module/apps/infoguard.mjs`.

## Порядок

1. **Раздели тесты и не-тесты.** Карточка теста несёт бросок и Порог. Уведомление («зона размещена», «истёк срок», «запрос теста») — не карточка теста: его НЕ переводи, а пометь коротким комментарием в коде, почему. Признак для поиска: есть ли рядом `roll-dice`.
2. **Не меняй вид без нужды.** Перевод обязан оставить карточку такой же, какой была: те же строки, тот же порядок, те же подписи. Если вид всё-таки меняется (например, слагаемые Порога переезжают в скобки к общему формату) — скажи об этом в отчёте отдельной строкой, это не мелочь.
3. **Достань подписи модификаторов.** Частый дефект этой задачи: `ruleMods.parts` собран, Порог посчитан верно, а в карточке стоит голое число. Проверь каждый файл своего списка: есть `collectTestMods`/`autoTestMods`, но нет ни одного `.parts` — значит модификатор посчитан и потерян по дороге к игроку. Подставь его.
4. **Сверь показанный Порог со считанным.** Второй дефект того же рода: карточка пишет `Порог: ${wp}`, а успех сравнивается с `wp + модификаторы`. Игрок видит не то число, по которому его судили.
5. **Убери осиротевшее.** После перевода `const rollMode = ...` и локальные `const messageData` обычно больше не нужны — их поймает lint, но лучше убрать сразу.
6. Гейты, с приведением вывода, а не памяти о нём:

```bash
npm test
npm run lint
```

`npm run packs:build` не нужен: карточки не трогают `packs-src/`.

Если полный `npm test` падает по `Test timed out` — это известная хрупкость (`wdbc-lxyl`), а не твоя поломка: перепроверь тем же прогоном с `npx vitest run --testTimeout=120000`. Красным считается только содержательное падение.

## Чего не делать

- **Не «улучшать» тексты карточек.** Формулировки книги и подписи — не твоя область. Меняешь только способ сборки.
- **Не трогать расчёт.** Если Порог считается неверно — это находка, `bd create`, а не правка на месте.
- **Не переводить карточки атаки** (`module/combat/attack-card.mjs` и его читатели): у них своя большая разметка с попаданиями, локациями и уроном, это отдельный разговор.

## Отчёт

Таблицей: файл, сколько карточек переведено, сколько помечено как «не тест», менялся ли вид. Отдельно — список того, что тронуть не смог и почему. В конце строка **«Для игры:»** — что изменилось для игрока за столом, без жаргона.
